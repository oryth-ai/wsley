# Deepening

在已有模块之间重新分配职责时使用本指南。术语沿用 [SKILL.md](../SKILL.md)。

## Find the owner

从一个具体用例画出最小调用链，记录每一步的规则、状态、依赖和失败路径。优先考虑这些有证据的候选：

- 多个调用者重复同一套校验、编排或清理流程。
- 修改一条业务规则必须同时理解多个只做转发的模块。
- 调用者需要知道存储布局、协议字段或内部执行顺序。
- 测试主要验证内部调用次数与顺序，重构内部结构就普遍失效。

确定最终由哪个模块拥有完整行为。目录相邻、文件短小或名称相似不足以支持合并；有独立生命周期、业务含义或调用者的模块可以继续分离。

## Classify dependencies

一个候选可能同时包含多类依赖，逐项处理，不给整个模块套用一种测试替身。

| 依赖类型 | 设计选择 | 验证方式 |
| --- | --- | --- |
| 进程内计算与状态 | 可在实现内部组合或合并；不为纯计算额外建立适配器层。 | 通过模块接口直接验证结果和状态转换。 |
| 本地可控资源，如文件系统、数据库 | 优先使用临时目录、隔离数据库或已有可靠替身；仅在需要替换的位置设置内部接缝。 | 验证真实资源语义；替身不能证明的事务、锁、权限或原子性由集成测试覆盖。 |
| 团队拥有的远程服务 | 模块拥有用例逻辑，以小端口表达所需能力，传输适配器处理协议与连接。 | 本地适配器验证业务行为，契约或集成测试验证真实传输、序列化和错误映射。 |
| 第三方服务 | 通过项目拥有的窄接口隔离 SDK 与供应商协议；只表达当前需要的能力。 | 使用受控替身验证成功、超时和失败分支；可用时用沙箱或契约验证适配器。 |

生产与测试适配器应遵守相同的结果、错误和状态约定。在内存适配器中成功，不代表网络、持久化或第三方协议已得到验证。

## Place seams deliberately

区分业务调用接口和构造时提供的依赖。调用者应提交业务输入，不应每次传递完整基础设施配置。测试需要替换下载器或时钟，不代表普通调用者必须了解这些内部协作对象。

保留明确的资源生命周期、取消与超时传播、错误归属。对于写入和远程副作用，说明部分成功、重试和幂等性的既有约束；重构不能悄悄改变这些行为。

## Move behavior and coverage together

1. 记录现有可观察契约与回归场景，特别是错误、副作用和顺序约束。
2. 通过目标接口建立行为验证，让内部结构可以改变；需要时保留复杂算法的精确测试。
3. 迁移行为与调用者，移除确认无引用的旧入口。是否保留兼容入口取决于项目契约和用户要求。
4. 按场景核对覆盖关系：只有已被新测试等价覆盖、或仅绑定已删除实现细节的旧测试才可移除。保留独有回归、协议与集成验证。
5. 运行受影响的现有检查，核对行为、依赖接缝和调用者负担。报告未验证的外部资源语义，不把 mock 通过描述为集成验证通过。
