# Design It Twice

在用户需要备选接口，或不同接口会明显影响调用方式、状态所有权和依赖位置时使用。术语沿用 [SKILL.md](../SKILL.md)；依赖策略需要时参见 [deepening.md](deepening.md)。

## Frame the decision

选定一个候选模块，收集真实调用场景、现有接口、必须保留的行为、依赖和代码位置。用简短说明固定各方案共同的约束；不要把第一版接口当成所有方案的前提。

## Explore different shapes

通常比较两到三个实质不同的方案，例如：

- 用例入口：一次调用完成常见流程，由模块拥有编排与清理。
- 显式会话或状态对象：支持确有需要的分阶段操作，明确生命周期和合法状态转换。
- 组合式能力：由调用者组合确实独立的操作，说明调用者因此承担的规则。

根据实际问题选择形态；只改名字、参数顺序或包装层不算备选设计。不要为使方案“不同”添加没有需求支持的灵活性。

每个方案给出：

1. 接口草图，以及不变量、顺序约束、错误与副作用。
2. 同一个真实用例的调用示例。
3. 模块内部隐藏的知识，以及仍由调用者承担的知识。
4. 依赖与接缝的位置、适配器依据和验证方式。
5. 迁移成本、主要收益与代价。

可以独立顺序推导方案；仅在当前环境允许且独立探索有实际价值时使用子代理。使用子代理时，为其提供相同的代码证据和约束、不同的设计侧重点，由主代理核对输出。不依赖特定工具名、固定代理数量或仓库中未必存在的文档。

## Compare and recommend

用相同场景比较各方案，不以接口方法数或代码行数单独决定优劣。

| 维度 | 核对问题 |
| --- | --- |
| 深度与接口收益 | 调用者要学习多少约定？多少真实规则得到集中处理？ |
| 变更局部性 | 一条业务规则或依赖协议变化，会影响哪些拥有者和调用者？ |
| 接缝位置 | 变化发生在哪里？替换依赖是否会迫使普通调用者改变？ |
| 正确性与验证 | 无效状态如何处理？失败路径能否从接口验证？真实依赖还需哪些验证？ |
| 迁移成本 | 哪些调用者和公开契约受影响？收益是否足以支持调整？ |

明确推荐一个方案并说明依据；若组合方案，重新展示组合后的完整接口与用例，检查它是否重新暴露了复杂度。任务只要求设计时交付建议；已授权实施时按选定方案继续，只有尚未明确且影响实现的关键决策需要用户补充。
