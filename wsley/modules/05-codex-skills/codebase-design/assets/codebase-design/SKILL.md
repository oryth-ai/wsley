# Codebase Design

设计深模块：用容易理解的接口承载完整行为，把调用者不必知道的复杂度集中到实现内部。目标是让调用更简单、变更更集中、行为能通过稳定接口验证，而不是增加抽象层或减少文件数量。

## Vocabulary

分析时使用以下含义；与项目已有领域术语对应，不为统一词汇而重命名现有代码。

| 术语 | 含义 |
| --- | --- |
| Module（模块） | 拥有接口和实现的行为单元，可以是函数、类、包或跨层功能切片。 |
| Interface（接口） | 调用者正确使用模块必须知道的全部约定，包括参数、返回值、不变量、调用顺序、错误、配置和必要的性能约束。不限于语言中的 `interface` 声明。 |
| Implementation（实现） | 模块内部完成行为的代码、状态与协作方式。 |
| Depth（深度） | 调用者学会少量接口约定后获得的行为能力，不以实现行数与接口行数之比衡量。 |
| Seam（可替换接缝） | 能替换行为而不修改该处调用逻辑的位置；接缝放在哪里与接口提供什么行为是两个决策。 |
| Adapter（适配器） | 在接缝处满足接口约定的具体实现，描述其角色而非代码规模。 |
| Leverage（接口收益） | 多个调用者和测试复用模块能力，不再各自承担同一复杂度。 |
| Locality（变更局部性） | 同一知识、规则、缺陷修复和验证集中在少数明确的拥有者处。 |

## Workflow

1. **确定范围与契约**：读取适用的仓库规范，明确用户需要分析、方案设计还是实际重构。记录要保留的可观察行为、公开契约和约束。只有关键产品或兼容性决策无法从代码确认时才询问。
2. **追踪真实调用链**：从相关入口沿调用者、状态拥有者、依赖和测试追踪行为。标注具体路径与符号，区分代码事实和推断。寻找调用者反复编排步骤、重复掌握内部规则、跨文件修改同一知识、为测试搭建大量内部 mock 等证据。
3. **评估模块深度**：列出调用者当前必须知道什么，以及哪些约定可以由模块内部承担。说明复杂度集中后谁更简单、谁需要改变；找不到明确收益时保留现有结构。处理既有模块簇及其依赖时，读取 [references/deepening.md](references/deepening.md)。
4. **设计接口与接缝**：用一个真实调用场景展示参数、结果、错误和必要的时序约束，再说明实现隐藏哪些规则、状态与外部依赖。用户要求备选方案，或接口选择有实质取舍时，读取 [references/design-it-twice.md](references/design-it-twice.md)。
5. **按任务范围交付**：分析任务给出有证据的建议；用户已要求实施时，完成相关调用者迁移和适当验证。报告接口变化、依赖策略、保留的契约和验证结果。不要把设计请求扩展成整个仓库重构。

## Design checks

- **计算完整接口成本**：一个带大量模式开关、隐含前提和调用顺序要求的方法，也可能是浅接口。减少方法数不能以增加认知负担为代价。
- **做删除思想实验**：假设移除模块，其职责会消失，还是重新分散到调用者？纯转发层需要说明独立价值，例如协议转换或策略隔离；不要仅凭“很薄”就删除它。
- **隐藏知识，保留职责**：把经常一起变化的规则放在同一拥有者处。深模块内部仍可由小函数和内部接缝组成，不把不相关职责塞进一个巨型模块。
- **用实际变化证明接缝价值**：生产与测试实现、外部协议隔离或明确的独立演进需求可以支持接缝。只有一个实现时先检查间接层的成本；不要为凑数量制造第二个适配器，也不要为假想扩展建立端口。
- **围绕可观察行为测试**：优先通过调用者使用的接口验证规则。必要时保留复杂算法的内部测试；不要为测试公开私有状态。接口更小可以简化测试准备，但不会减少应覆盖的业务行为。
- **隔离不确定性**：把时间、随机性、文件系统和远程服务放到有理由的接缝处。纯计算优先返回结果；必须产生副作用的模块应明确副作用、失败语义和重试约束。

## Example

发布器原先要求每个调用者依次执行 `download`、`verifyChecksum`、`stage`、`activate` 和失败清理。一个完整的用例接口可以是：

```go
result, err := installer.Install(ctx, release)
```

接口约定必须说明校验失败是否保留旧版本、激活是否原子化、取消后的状态以及调用者可区分的错误。下载、校验、临时目录和清理由实现协调；下载源可以在构造时注入，普通调用者不必逐次组装内部步骤。

通过 `Install` 验证成功安装和失败后旧版本仍可用；原子替换的文件系统语义需使用真实临时目录验证。若确有调用者需要单独下载，则根据该用途保留独立能力，不强行合并所有入口。

## Reporting

让建议可核对：给出当前问题的代码位置、建议接口及调用示例、隐藏的复杂度、接缝依据、测试方式和主要取舍。按实际发现的收益排序，不为满足数量而列出重构项；没有值得调整的模块时明确说明依据。
