# Git Review

在提交前对照任务要求、项目规范和最终文件审计相关改动，修正遗漏、违规和实现不一致，使交付内容达到可提交状态。审计覆盖本次任务的完整结果，不以 diff 行数、格式检查或测试通过代替完整性判断。

按当前请求确定只读审计或审计并修正。当前开发任务已授权必要修正，或用户明确要求审计并优化时，在该范围内修正有依据的问题；用户仅要求审查、报告或建议时，交付发现与建议。技能被加载不构成额外授权，审计不自行包含暂存、提交、推送或修改历史。

## 确定范围与依据

以当前任务已明确的目标、修正意见和决定为审计依据，按需要读取适用于修改路径的 `AGENTS.md`、`CONTRIBUTING.md`、领域文档及相关配置。区分项目明确要求、已有实现习惯和可选建议，以用户要求及实际适用规范判断问题，不将个人偏好或本技能的示例升级为项目规则。

检查当前分支、`git status --short`、`git diff --cached`、`git diff` 和未跟踪文件清单，逐项读取本次任务涉及的内容，包括新增文件、删除、重命名和关联资源。区分本次改动、用户已有修改和其他任务的变更；审计可以指出关联风险，修正只落在当前授权范围内。

分别理解暂存区准备提交的版本和工作区的最终版本，必要时通过 `git show :路径` 读取暂存的完整文件。同一文件存在两种版本时，确认修正实际位于哪一层；工作区已经修好不代表暂存内容可以提交，暂存内容完整也不代表工作区没有遗漏。保留用户的部分暂存安排，不通过全量暂存、重置或覆盖文件消除差异。

任务依据缺失且影响正确性、审计范围或修正方案时，只澄清该缺口，继续不依赖它的工作。范围未明确时先识别当前相关改动，不自行审计整个仓库历史或清理其他任务。

## 审计完整结果

通读受影响文件，沿调用、配置和资源引用核对实际行为。根据项目约束检查以下方面，不要求每个项目套用同一套结构：

| 方面 | 判断依据 |
| --- | --- |
| 任务完成度 | 已确认的要求、例外和反馈是否落实，是否存在未完成分支、占位实现或任务外行为变化 |
| 项目规范 | 职责边界、目录归属、命名、语言、注释、文件格式和工具使用是否符合适用规范 |
| 实现一致性 | 接口、调用方、错误处理、配置、组件清单、依赖、资源与说明是否采用同一方案 |
| 变更完整性 | 新增文件是否纳入审计，删除与重命名是否更新引用，被替代的实现、入口和说明是否仍能生效 |
| 验证有效性 | 检查是否覆盖真实变更与关键失败路径，验证对象是否与准备提交的内容一致 |

对每项问题找到具体文件或调用链，以及对应的任务要求、规范或可复现行为。区分必须修正的问题、影响待确认的风险和可选改进，不靠模糊的“更优雅”“更安全”扩大修改。与任务无关的历史问题单独说明，不混入本次修正。

留意误入交付的临时产物、调试内容和敏感数据；说明问题时隐藏敏感值，不将其复制到报告或提交信息。

## 修正与验证

已授权修正时，先处理有明确依据且影响任务完成、项目规范或行为正确性的问题，在负责该行为的位置解决原因，并同步受影响的调用方和资源。需要调整相关结构时保持任务范围，避免为了消除局部问题增加重复规则、转发层或无实际用途的抽象。

遵循已有的文件修改权限和文档约定，不通过弱化规则、修改协作规范、删除有效检查或放宽测试断言使改动表面合规。项目规范本身属于用户明确要求调整的内容时，按该授权处理。

按审计模式和仓库要求选择格式检查、静态检查、构建或行为验证；只读审计时不执行会改写被审计文件的格式化或自动修复。验证对象以实际变更为准，修正后核验直接受影响的行为；已通过且不受修正影响的结果可以复用。缺少环境或关键验证失败时，说明具体限制和未完成部分，不将未执行的检查标为通过。

修正完成后重新检查最终差异、完整文件和关联引用，确认没有引入任务外变更、失效说明或漏掉的新文件。若工作区修正尚未进入暂存区，交付时指出该差异；只有获得对应授权时才更新暂存内容，并重新核对实际准备提交的版本。

## 审计结果

简要说明审计范围、已修正的问题及依据、验证结果和仍需处理的事项。未发现明确问题时直接说明，不为凑齐发现而制造修改；存在未验证部分时限定结论，不把“未发现问题”表述为保证没有缺陷。
