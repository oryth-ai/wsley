# Git Review

在提交前以项目规范和工程结构为主线审计相关改动，重点核对目录职责、代码组织、内容规范、完整切换和产物归属，并在授权范围内修正问题。任务要求用于确定审计范围和必须保留的行为；功能检查用于识别明显回归、契约冲突及结构修正的影响，作为辅助证据。格式检查、构建或测试通过不能代替规范与结构审计。

按当前请求确定只读审计或审计并修正。当前开发任务已授权必要修正，或用户明确要求审计并优化时，在该范围内修正有依据的问题；用户仅要求审查、报告或建议时，交付发现与建议。技能被加载不构成额外授权，审计不自行包含暂存、提交、推送或修改历史。

## 确定范围与依据

以当前任务已明确的目标、修正意见和决定为审计依据，按需要读取适用于修改路径的 `AGENTS.md`、`CONTRIBUTING.md`、领域文档及相关配置。区分项目明确要求、已有实现习惯和可选建议，以用户要求及实际适用规范判断问题，不将个人偏好或本技能的示例升级为项目规则。

检查当前分支、`git status --short`、`git diff --cached`、`git diff` 和未跟踪文件清单，逐项读取本次任务涉及的内容，包括新增文件、删除、重命名和关联资源。区分本次改动、用户已有修改和其他任务的变更；审计可以指出关联风险，修正只落在当前授权范围内。

分别理解暂存区准备提交的版本和工作区的最终版本，必要时通过 `git show :路径` 读取暂存的完整文件。同一文件存在两种版本时，确认修正实际位于哪一层；工作区已经修好不代表暂存内容可以提交，暂存内容完整也不代表工作区没有遗漏。保留用户的部分暂存安排，不通过全量暂存、重置或覆盖文件消除差异。

任务依据缺失且影响正确性、审计范围或修正方案时，只澄清该缺口，继续不依赖它的工作。范围未明确时先识别当前相关改动，不自行审计整个仓库历史或清理其他任务。

## 目录结构与职责

先浏览仓库顶层布局，再列出受影响模块内完整的文件与子目录结构，结合相关父级目录、同类相邻模块及引用关系判断归属。目录检查包括未改动但共同承担该职责的文件，不只查看 diff 中的路径或抽查新增文件；审计范围仍围绕本次任务及其必要影响，不扩展为逐文件清理全仓。

核对每个新增、移动或拆分的文件与目录承担什么职责，当前放置位置是否符合项目约定，是否与已有实现重复或使同一职责分散。重点检查无实际作用的嵌套目录与转发层、过度拆分、职责混杂，以及搬移后留下的空壳入口或失效结构。文件数量、目录深度或代码行数只能提供线索，不能单独作为违规依据；语言、构建或工具要求的结构按其实际用途保留。

分别核对准备提交的目录结构与工作区最终结构。新增文件、删除、重命名或部分暂存导致两者不一致时，说明各自的结构问题，不能用工作区中尚未暂存的搬移掩盖提交内容的缺陷。

## 规范与完整性

通读受影响文件，沿调用、配置和资源引用核对最终结果。先完成以下规范与结构检查，再按实际影响选择功能验证；具体判断服从适用项目规范，不将示例中的组织方式套用到所有项目。

| 方面 | 判断依据 |
| --- | --- |
| 目录与职责 | 文件归属、职责边界及目录层级是否清晰，是否存在无实际用途的嵌套、转发、拆分或职责混杂 |
| 代码组织 | 命名、函数边界、逻辑分组、排列与空行是否符合约定，是否存在重复实现、分散规则或掩盖结构问题的特殊补丁 |
| 内容规范 | 日志、注释、文档和配置说明的语言、表述与格式是否符合规则，说明是否与最终行为一致，是否残留调试或过程性内容 |
| 完整切换 | 被替代的入口、符号、依赖、配置、资源和说明是否清理，调用方、组件清单及生成物是否同步，新增交付内容是否遗漏 |
| 产物归属 | 测试、一次性验证脚本、临时材料与生成文件是否放在项目规定的位置，是否存在不应进入提交的产物 |

对每项问题找到具体文件或调用链，以及对应的任务要求、规范或可复现行为。区分必须修正的问题、影响待确认的风险和可选改进，不靠模糊的“更优雅”“更安全”扩大修改。与任务无关的历史问题单独说明，不混入本次修正。

留意误入交付的临时产物、调试内容和敏感数据；说明问题时隐藏敏感值，不将其复制到报告或提交信息。

## 修正与验证

已授权修正时，围绕有明确依据的规范与结构问题，在负责该行为的位置解决原因，并同步受影响的调用方和资源。需要调整相关结构时保持任务范围，避免为了消除局部问题增加重复规则、转发层或无实际用途的抽象。

遵循已有的文件修改权限和文档约定，不通过弱化规则、修改协作规范、删除有效检查或放宽测试断言使改动表面合规。项目规范本身属于用户明确要求调整的内容时，按该授权处理。

执行项目要求的检查，并按审计模式和修正影响补充必要验证；只读审计时不执行会改写被审计文件的格式化或自动修复。目录搬移重点核对引用、导出与资源路径，接口调整核对相关调用，纯规范修正按实际影响选择检查，不自行扩展为完整业务验收。发现有证据的明显回归或契约冲突时仍需记录和处理，不能因规范审计为主而忽略。

验证对象应与准备提交的版本一致，已通过且不受修正影响的结果可以复用。缺少环境或关键验证失败时，说明具体限制和未完成部分，不将未执行的检查标为通过。

修正完成后重新检查最终差异、完整文件和关联引用，确认没有引入任务外变更、失效说明或漏掉的新文件。若工作区修正尚未进入暂存区，交付时指出该差异；只有获得对应授权时才更新暂存内容，并重新核对实际准备提交的版本。

## 审计结果

简要说明实际检查的目录范围、所依据的规范、发现与修正、验证结果和仍需处理的事项。先报告规范与结构审计结论，再说明辅助验证；不能只列测试结果就宣布审计完成。重要目录或规范未检查时，明确该缺口。

未发现明确问题时直接说明，不为凑齐发现而制造修改，也不机械罗列空的问题类别；存在未验证部分时限定结论，不把“未发现问题”表述为保证没有缺陷。
