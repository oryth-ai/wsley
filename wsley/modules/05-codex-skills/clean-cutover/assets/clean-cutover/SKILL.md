# Clean Cutover

执行一次干净切换：新内容成为项目中唯一的权威实现，旧内容从代码、配置、文档、测试和交付物中收口移除。把“直接替换”当作完成标准，而不是在新旧方案之间长期维持双轨。

## Workflow

1. **确定唯一目标**：读取适用于修改路径的 `AGENTS.md`、项目文档、契约和测试，提炼新行为、公开名称、数据形状与验收条件。若用户要求的目标与现有规范冲突，先报告冲突；不要自行把目标降级为兼容方案。

   完成条件：目标实现、目标名称、受影响边界和可观察验收条件均已明确，并且没有把旧行为列为目标行为。

2. **盘点旧表面**：在修改前搜索旧名称、旧路径、旧字段、旧配置键、旧 API、旧测试夹具和相关文案，覆盖源码、测试、文档、配置、脚本、生成物与资源。结合调用关系确认每个引用的拥有者和替换位置。

   完成条件：旧表面的清单覆盖所有搜索命中及其直接消费者；清单明确哪些文件需要改写、删除或重新生成。

3. **直接改写**：在原有行为拥有者处实现新契约，并同步更新所有消费者。让新名称、新结构和新流程贯穿实现，不保留旧入口的别名或转发层。需要删除的文件、符号、配置和资源在确认引用已迁移后直接移除。

   目标实现必须保持单一路径：使用新的 API、字段和配置；不添加旧新并行读取/写入、版本分支、feature flag fallback、deprecated wrapper、adapter、兼容别名、隐式回退或仅为历史保留的注释与文档。

   新增和改写内容必须融入原文件的组织结构，与上下文的抽象层级、术语、语言风格和格式约定保持一致。涉及同一事项时，原位整合相关段落或实现，必要时调整相邻内容的衔接，避免孤立追加、重复说明或局部风格突变。正文和注释应直接描述最终状态，不保留“本次新增”“修改后”等修订过程说明、临时补充标记或新旧方案对照，使文件呈现为连贯、统一的完整成果；项目要求的变更记录和迁移历史仍按各自规范维护。

   完成条件：项目中每个受影响消费者都已接入目标契约，旧入口和旧资源已从工作树移除，运行时不存在根据新旧格式或版本选择行为的分支。

4. **收紧验证**：先用精确旧标识和旧路径重新搜索，再检查 diff 是否包含删除与替换的完整闭环，并通读修改后的文件，确认新增内容在结构、语义和表达上与上下文自然衔接；随后运行项目已有的格式检查、静态检查、单元测试和相关集成测试。对 API、CLI、配置或 UI 改动，验证公开入口只暴露新行为。

   完成条件：旧标识的搜索结果为空（仅允许明确属于测试断言的负向检查）；目标行为的测试通过；diff 中没有备份文件、归档副本、临时迁移残片或未解释的兼容代码；修改后的文件整体一致，不存在补丁式拼接、重复表述或修订过程残留。

## Data and migrations

需要保留已有数据时，采用一次性的单向迁移把数据转换为目标格式，再让运行时只认识目标格式。迁移完成后删除临时双读、双写和回退逻辑；只有项目明确要求可重复部署的迁移历史时才保留迁移文件，并确保它不参与运行时兼容判断。

## Boundaries

- 直接替换针对用户明确纳入范围的项目内容；保留无关改动，并只修改完成切换所需的文件。
- 删除前先确认具体目标和引用关系，使用可恢复、精确的文件操作；不要对宽泛目录执行清理。
- 发现目标契约仍缺少关键决策时，指出具体决策点并暂停该部分实现；不要用兼容层掩盖不确定性。
- 不把 Git 提交、推送、发布或外部系统变更视为默认步骤；只有用户明确要求时才执行。
