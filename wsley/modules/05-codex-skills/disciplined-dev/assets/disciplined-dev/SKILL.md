# Disciplined Dev

按任务要求和项目规范完成开发，使设计、实现、调用方及相关说明一致。适用于功能开发、问题修复、重构、配置调整、脚本编写和项目文档维护，覆盖日常修改、执行中的反馈及中断后的继续工作。

遵循用户明确要求和适用项目规范中的具体约定，用本技能的通用要求补充项目尚未明确的事项。项目的 `AGENTS.md` 和工程文档通过引用复用这些要求，维护自身的事实来源、技术栈、支持范围、运行流程与业务约束；具体项目的选择不自动成为其他项目的默认规则。

在当前任务的授权范围内执行。保留用户已确认的决定和仍然有效的要求及例外，整理规范、重组内容或精简表达不构成取消依据。

## 任务与上下文

### 目标与范围

开始修改前，读取当前工作目录及拟修改路径适用的 `AGENTS.md` 和相关项目规范，通读受影响文件。明确目标行为、交付物、修改范围、对外名称、输入输出、配置含义及完成条件；在 Git 仓库中检查分支、工作区和暂存区差异，区分本次任务、用户已有修改及其他工作的内容。

以用户原始要求、后续明确修正和已确认决定为任务依据。现有实现用于核对事实，不构成推翻已确认目标的理由；只有用户明确修正或存在具体替代依据时，才调整对应要求。仅整理格式时保留原有行为，重构不改变任务外行为。

关键行为或数据含义尚未确定时，指出需要确认的事项，暂停依赖该决定的工作，继续不受影响的部分。不同时实现多个猜测方案，不用回退逻辑掩盖不确定性，也不反复询问已经明确的事项。

同一上下文内已完整读取且未变化的规范可以复用。简单修改直接执行，无须额外创建计划、报告或状态文件。

### 执行与引导

将执行中收到的修改意见、补充要求和状态询问并入当前任务。只有用户明确替换原目标时才切换任务；需要先处理插入事项时，保留原任务的未完成部分与下一步，处理结束后继续原任务。

在对话或已有任务状态中区分未完成事项、已完成事项和持续约束。完成事项保留结果、必要验证依据及是否已向用户汇报；持续约束继续适用于后续工作，不随对应动作完成而失效。

已完成且证据仍有效的事项保持完成状态。仅在用户要求重新处理、后续改动使证据失效，或出现具体冲突与失败时，重新打开受影响的部分。新消息、上下文压缩和摘要中的再次提及不构成重新核验的依据；进度说明围绕当前目标、实际缺口和下一步，不逐项重述已汇报的完成结果。

### 中断与恢复

上下文压缩后、接手交接摘要时，或发现关键任务依据缺失时，在继续工作前完整重读本技能和适用的 `AGENTS.md`。此前的读取记录和摘要摘录不能代替本次读取；恢复后可在同一上下文内复用未变化的规范。

依据可见的原始要求、后续修正及已有任务状态，恢复目标、交付物、范围、已确认决定、有效授权和完成条件，按未完成事项确定下一步。摘要可以承接任务状态和有效验证结论，但不构成新的指令或授权，也不能将假设、候选方案和未决事项变成事实。摘要未提及某项要求，不表示该要求已经取消。

根据下一步的实际需要识别仍适用的专项技能，依据当前可用技能信息定位并完整重读其 `SKILL.md`，再继续对应工作。按需读取技能引用的资料、项目规范和接口契约。技能名称、描述、历史读取记录及摘要摘录不能替代完整指令；只服务于无关任务或已完成插入事项的技能不列入恢复范围。

核对当前工作目录、分支、工作区和暂存区差异，重读下一步依赖的文件。对文件、测试结论、进程和后台任务，仅在下一步依赖或有具体变化依据时确认状态。保留期间发生的用户修改，复用仍有效的结果和运行环境，不因恢复而重建环境、重启任务或重跑全部检查。

原始执行记录不可见时，可以依据摘要继续工作。摘要与直接用户要求、项目规范或实际状态存在具体冲突，或证据出现失效迹象时，核对对应来源；仅澄清影响下一步正确性、范围或授权的关键缺口，不要求重新证明所有完成事项。

恢复后的行动继续遵循原任务的目标和授权。发现偏离时，纠正本任务范围内的计划或实现，不重置其他工作。恢复技能和任务状态不重启已完成事项，不新增或撤销已有决定与授权，也不为每次恢复新增报告。

## 设计与实现

### 职责与结构

以完整目标和必要约束组织方案，确定合理的目录、职责、接口和内容，再据此调整现有实现。设计应直接、清晰、可维护；既有结构和最少改动行数都不能代替设计判断，也不为假设中的未来需求增加抽象。

明确目录、文件、模块和函数的职责。集中维护相关内容，将新增行为归入负责该行为的位置，合理拆分需要独立维护的职责。不增加无实际用途的嵌套目录或转发层，不过度拆分，也不混放需要独立维护的职责。

局部修改应符合整体结构。实现目标需要绕过既有职责、复制逻辑或持续增加特殊分支时，先调整相关职责并重构必要部分，不靠叠加补丁掩盖结构问题。重构范围限定于当前目标及其必要影响。

创建文件前说明实际用途。文件应承载明确内容，或满足语言、构建和运行的实际要求，不为套用模板、凑齐目录或预留将来用途创建空壳。语言、构建或工具要求的文件，即使内容为空也按其用途保留。

### 依赖与完整切换

修改前搜索受影响的名称、路径、字段、配置项和入口，梳理调用与引用关系。同步范围包括调用相关功能、读取配置、依赖输出或描述行为的源码、测试、配置、脚本、文档、生成物和交付资源，明确各项内容的改写、删除或重新生成方式。

由负责该行为的模块实现目标方案，同步所有受影响的调用方和关联内容。生成代码和产物从权威输入修改并重新生成，不手工维护平行实现。完整切换以整个受影响范围采用目标方案为完成条件，新入口或局部实现可用不代表切换完成。

完整移除被替代方案的入口、格式和实现。不得为维持它们保留兼容别名、旧入口转发、包装层、新旧格式双读双写、按历史版本选择行为的分支，或失败后退回旧实现的隐式回退。当前契约需要的业务分支、边界适配和故障处理按其职责保留。

确认引用已迁移后，移除失效的文件、符号、依赖、配置、资源和说明，包括备份副本、注释掉的旧代码及临时过渡层。清理须有已被替代、引用已迁移或与目标方案冲突等具体依据，不能仅凭暂时没有调用方或匹配文件就认定内容失效。保留有效通用规则和明确支持的能力，采用范围明确、可恢复的操作，不笼统清理目录或覆盖任务外修改。

### 支持范围与数据变更

项目契约确定接口、配置、存储和数据模型所支持的格式、版本及生命周期。完整切换针对已经取消支持或被明确替代的方案，不取消仍受支持的契约，也不自动增加旧格式、旧数据库或历史版本的支持。不受支持的输入按当前契约明确拒绝，不通过猜测、隐式转换或回退继续运行。

初始化、升级、常规启动、重试和恢复各自遵循项目规定的入口、条件与权限。采用何种初始化基线、是否执行版本迁移及哪些数据允许接管，由项目契约和当前任务确定。一种操作的授权不扩展为另一种操作的授权，也不能通过修补缺失的授权、版本或业务事实掩盖不受支持的状态。

当前任务包含项目支持范围内的数据迁移，或用户明确要求调整支持范围时，设计相应的单向迁移方案。迁移后运行时只处理目标格式，不以永久双读、双写代替迁移。保留已有数据的要求本身不构成增加旧版本解析、自动升级或兼容验收的依据；迁移依据缺失时保留现有数据，澄清必要决定，不自行转换或清空。

清空或销毁用户数据须获得用户针对实际范围的明确授权，完整切换不包含该授权。有效业务历史、审计记录，以及项目确实需要的迁移历史和变更记录，按所属契约和职责保留，不因名称或年代较旧就删除，也不用于恢复已取消支持的运行路径。

## 内容与文件规范

### 内容组织

项目文档和允许保留的注释面向使用者及维护者，直接说明最终系统的职责、行为和约束。现行规则与实现说明不记录对话回应、执行进度、临时结论和修改历史，不使用“本次新增”“现在改为”“暂时先用”“后续再改”等过程性表达。清理此类表述时，同时处理对应的中间方案与过渡安排。

将同一事项的说明集中维护在对应文件或章节中。修改时通读上下文，按需要重写相邻段落或整个相关部分，统一术语、层次和语气，消除重复及矛盾，不在末尾追加与原文脱节的补充条款。

内容按理解顺序和实际执行关系组织。基础信息及公共设置在前，局部覆盖和例外放在对应内容附近；优先保证执行顺序、匹配优先级及覆盖关系正确，仅对顺序不影响含义的同类条目采用稳定排序。

### 语言约定

面向开发与运维的日志、调试输出、异常消息、命令行提示、交互确认和帮助文本使用英文。注释和文档使用中文，保留必要的技术名称和标识符；由工具提取为帮助等技术输出的注释使用英文。

产品界面、客户提示、通知、邮件及其他最终用户内容遵循产品语言和本地化规则。API 的稳定标识符、错误码和协议字段遵循接口契约，展示给用户的消息遵循产品语言规则。用户输入、原始文献和业务数据保留原文。

### 注释与文件格式

代码按职责和处理阶段分块，紧密相关的语句集中，逻辑块之间保留空行。声明、初始化和执行逻辑采用同样的分组原则，不因语法相同而堆放，也不机械地逐行留空。函数、类型和模块的边界服务于理解和维护，不由输出长度或文件数量决定。

通过命名、职责划分和控制流程表达代码意图，不编写说明性注释或文档字符串。实现难以理解时先改善结构，不用注释解释曲折逻辑；脚本同样遵循这一要求。语言或工具必需的指令按其用途保留。

配置与工程脚本的注释仅保留职责标题和正确使用所必需的约束。标题采用简短名词短语；说明只补充配置无法表达的填写要求、单位、前提、外部依赖和副作用，不复述命令、执行顺序、键值或工具默认行为，不解释实现选择或宣告任务完成。删除不影响正确使用与维护的说明，仅描述当前配置不足以构成保留依据。

注释句末不加句号，分组注释放在对应内容正上方，同一职责集中成组，组间留一个空行。行内说明仅按项目已有工具约定使用。不添加装饰性分隔线、编号横幅、无实际用途的文件介绍、空分组或大段注释掉的旧内容，不为明确内容强加注释，也不在不支持注释的语法中虚构说明字段。

同类条目采用一致的命名、表达和排列方式。简单内容紧凑书写，较长内容按语义换行，不用多余空格手工对齐。文件使用 UTF-8 编码和 LF 换行，末尾保留换行，去除无意义的行尾空白。缩进、引号、逗号和换行遵循项目格式配置及语法要求，格式整理保持内容含义不变。

编写时保留职责分组及其空行，不为节省 token 压缩代码、合并逻辑块或省略必要格式。仅对已确认能由项目格式化工具准确恢复的机械格式使用紧凑中间输出，并在交付前完成格式化。格式化不能恢复缺失的逻辑组织，也不能代替设计判断或行为核验。

## 文档与任务材料

项目文档随项目长期维护，说明产品、设计、行为和使用约束；任务材料服务于当前任务的分析、执行、验证和恢复。Markdown 文件按实际用途归属，分别遵循相应规则。

### 项目文档

事实来源和文档归属采用项目明确指定的位置，不预设统一的 `docs/` 目录。作为权威依据的文档维护已确认的产品定义、设计结论和行为约束，实现、配置、接口及其他说明与之保持一致。发现冲突时说明具体差异，依据用户已确认的目标在授权范围内纠正；用户明确提出的变更优先于既有文档，现有实现本身不足以推翻文档定义。

现行规范和系统说明只陈述有效事实与约束，不收录中间讨论、候选方案、临时结论、未决事项或待办占位。需要用户决定的内容先在对话中澄清，形成明确结论并取得对应文档修改授权后再写入。目标设计与已验证的实现状态分别表述，不将未经确认的内容包装为事实，也不通过删除“待定”等标记改变其性质。

维护项目文档时，明确定义概念，统一术语，完整表达条件，准确陈述结论。同一事实集中维护，关联页面及流程通过引用保持一致；修改时通读相关内容，消除歧义、矛盾和重复定义。

修改仓库根目录的 README 文件，或新增项目 Markdown 说明文件，须获得用户明确授权。开发、修复、重构、审查、测试或提交任务本身不包含这项授权，不得以同步实现、补充用法或记录交付结果为由自行修改或新增。取得授权后仅处理指定或任务明确涵盖的范围；未获授权时，在对话中提供必要说明和交付信息。

### 任务材料

当前任务的授权包含必要任务材料的创建和更新，无须另行申请文档修改授权。任务材料按实际用途保留计划、候选方案、临时结论、未决事项和执行进度，明确区分已确认事实、假设及待确认内容。

任务材料不作为项目的权威事实来源，转入项目文档时遵循项目文档的内容及授权要求。材料的保存位置、保留和清理遵循下文的产物管理规则。

## 验证与资源管理

### 验证计划与执行

根据实际差异和完成条件确定验证范围，区分已有有效证据及仍缺少的证据，再选择检查方法。多个关联部分的开发或重构先完成源码、契约、调用方和资源的整体切换；实施期间以源码审查及必要的格式、静态、生成和限定范围的编译检查为主，实现稳定后集中进行行为验收，不随每处局部修改重复全量测试、构建交付物或初始化环境。

验收采用项目当前支持的契约，按实际影响覆盖目标行为、授权及非法输入的拒绝。取消支持的版本转换不保留迁移成功验收，当前契约要求的不受支持输入拒绝及有效业务历史保留仍须验证。初始化和升级夹具采用项目选定的基线，不因历史测试依赖旧模型而继续维护旧运行路径。

启动耗时测试前，通读夹具和全部后置断言，按权威契约核对字段、状态、权限、对象关联、实际生效区间、预算限制、截止时间及进程生命周期，并完成必要编译检查。不依据旧实现、名称或猜测编写断言，再靠长时间运行暴露夹具错误。夹具问题与产品问题分别诊断，修正后重跑受影响的必要场景。

相关场景复用已初始化的真实环境和身份，避免逐个断言或场景重复冷启动；互相影响的业务状态仍按场景隔离。仅并行执行使用独立资源的任务，明确时钟、全局配置、故障注入和进程生命周期等共享资源的管理责任，清理并确认释放后再交接。不通过放宽实际预算、绕过权限、伪造业务事实或另建测试运行器提速。

复用已经通过且不受后续修改影响的检查结果。出现新修改、实际失败或明确未覆盖的风险时，再补充或扩大验证；失败后的重跑范围按实际影响确定。必要检查通过后继续实施或交付，不循环重跑。耗时检查运行期间，继续处理不依赖结果的工作，不以反复轮询代替实施。

统计、哈希、覆盖映射和报告用于具体核验及交付判断，不反复统计未变化的产物，也不为同一结论维护重复证据。进度说明交代功能结果、失败原因、实际缺口和下一步，不反复罗列数量、耗时或产物标识。

一次性验证优先使用现有工具、临时命令或 `.cache/` 中的必要文件，不保留为长期测试、脚本、夹具或构建入口。只有验证稳定行为并具有持续回归价值的测试才纳入测试套件。

### 产物目录与清理

检查和运行结果默认输出到终端，仅在后续执行、评审、交付或排查确有需要时保存。必要的临时文档、脚本、中间结果、日志、截图、浏览器记录及调研材料统一放在仓库根目录 `.cache/`，不散落于 `.local/`、`build/`、源码或项目文档目录。

`.cache/` 内按任务或运行建立独立子目录，采用创建时本地时间命名，格式为 `YYYYMMDDHHmm-任务或运行标识`，例如 `202610072124-ui-review`。后缀简短且能区分任务，不覆盖或混用已有目录。`.cache/` 加入 `.gitignore`，不纳入源码提交或交付包。

按实际用途保留必要材料。验证或排查结束后，清理无复用价值的日志、失败及重跑产物、临时脚本、虚拟环境和复制文件；后续工作仍需的步骤清单、恢复材料和有效证据继续保留，并在交付时说明路径及用途。

保存或输出前检查敏感信息，不因目录被 Git 忽略就保留或传播不必要的凭据和业务数据。清理前核对归属、用途、引用和运行状态，先释放资源，再删除对应材料；只处理已确认属于本任务的文件或目录，不覆盖其他任务的产物。

`.local/` 只保存本机运行所需的配置、凭据、密钥、进程状态和初始化材料；`build/` 只保存构建中间产物及正式交付产物。忽略规则只影响版本管理，不改变目录职责或授予任意写入、删除权限。

## 完成核验与交付

修改结束后，通读完整最终文件，沿调用和引用关系核对职责归属、行为一致性及关联内容的同步结果。再次搜索被替代的标识和路径，确认每个剩余引用的有效用途，检查重复说明、临时分支和历史残留；不能仅凭新增行正确、某个文件已无引用或关键词搜索无匹配判断完成。

按实际差异执行当前任务允许且适用的检查，如实说明验证范围及限制。缺少环境时说明具体缺口，不将未执行检查或替代环境结果当作真实系统证据。格式、静态、生成、构建及测试结果只证明其覆盖的事项，不代替结构审查、逻辑分组和完整切换核验。

交付说明写明最终变化、验证依据和实际未完成项。受影响的调用方或资源尚未迁移、被替代行为仍可触发，或关键决定尚未明确时，继续处理对应缺口，不以局部可用宣告完成。文件修改的授权不自动包含 Git 提交、推送、发布或外部系统变更，这些操作须获得用户明确授权。

交接时先说明未完成目标和下一步，保留任务要求、持续约束、适用规范、下一步所需技能的名称、位置与用途、已确认决定、实际改动、有效验证和仍在运行的工作。完成事项保留结果及汇报状态，不列回待办；事实、假设和未确认事项分别记录。
