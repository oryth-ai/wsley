# Coherent Change

从完整目标组织修改，使职责、行为、消费者和说明构成一致的成果。使用本技能理解目标、组织内容、实施修改、验证结果和完成交付，适用于功能开发、配置调整、脚本编写及已有实现的重构。成果应结构清晰、表达一致、没有被替代方案的残留；格式合规不能代替合理设计，重构也不能改变任务外行为。

先读取适用的 `AGENTS.md` 和项目规范。本技能不扩大用户授权；用户明确要求及项目规范中的具体约定优先。下文的目录、语言和文档规则作为未被项目具体约定覆盖时的默认规范。

> 修改适用的 `AGENTS.md` 须获得用户明确授权。开发、修复、重构、审查或提交任务本身不构成授权；不得因任务需要自行追加规则，也不得将项目实现、操作说明或开发过程回写到协作规范。

## 工程实施与交付

### 目标与修改边界

开始修改前，通读受影响文件和适用规范，检查工作区已有差异，区分本次任务、用户已有修改及其他工作。明确目标行为、对外名称、输入输出、配置含义和完成条件。仅整理格式时，保留原有行为；用户已经确认的决定持续有效，不因现有代码采用另一种方式而自行推翻。

方案采用“最优切换”原则：以完整目标和必要约束为依据，确定如果从一开始就实现该目标，应如何组织目录、划分职责、定义接口和编写内容，再将现有实现调整到这一形态。现有文件用于核对事实和依赖，不能因其已经存在就认定设计合理。最优方案应直接、清晰、可维护，不以改动行数最少为标准，也不为假设中的未来需求增加抽象。

局部修改应融入完整结构。接入功能若需要绕过既有职责、经过无意义的转发层、复制逻辑或持续增加特殊分支，应先重新划分相关职责并重构必要部分。不得叠加补丁掩盖结构问题；重构范围限定于目标及其必要影响，不借机重写无关模块。

关键行为或数据含义尚未确定时，明确缺少的决定，暂停依赖该决定的部分，继续处理不受影响的工作。不得同时支持多个猜测方案，也不得用回退逻辑掩盖不确定性。

### 职责与代码结构

目录、文件、模块和函数应表达明确职责。相关内容集中维护，新增功能归入负责该行为的模块；职责不同或需要独立维护的边界应合理拆分。不得增加没有实际作用的嵌套目录、转发层或过度拆分，也不得以简洁为由将不同职责塞进同一个文件。

创建文件前，说明其实际用途。文件应承载明确内容，或满足真实的语言、构建、运行要求；不得为套用模板、凑齐目录形式或预想将来使用而创建空壳。语言、构建或工具要求的文件不得仅因内容为空而删除。

代码通过命名、职责划分和控制流程表达意图，不编写说明性注释或文档字符串。难以理解的实现应先改善结构，不用注释解释绕行。语言或工具必需的指令不属于说明性注释；配置与工程脚本面向使用者的分组和使用约束按下文维护，脚本实现逻辑仍应通过清晰结构表达。

代码按职责和处理阶段组织逻辑块，紧密相关的语句置于同一块，块间保留空行。声明、初始化和执行逻辑同样按职责分组，不因语法形式相同而堆放，也不机械地逐行留空。不同处理阶段不得连续堆叠，同一紧密逻辑不得无意义拆散；函数、类型和模块的边界服务于理解和维护，不服从输出长度或文件数量指标。

### 消费者与完整切换

“干净切换”要求目标方案成为受影响范围内唯一有效的实现和说明：所有消费者同步使用目标方案，被替代的路径及其残留退出当前项目。新增代码或新入口可运行不代表切换完成；最优切换确定最终形态，干净切换确保项目完整到达这一形态。

修改前，搜索受影响的名称、路径、字段、配置项和入口，结合调用与引用关系识别消费者。调用功能、读取配置、依赖输出或描述行为的内容都属于消费者。盘点应覆盖相关源码、配置、脚本、文档、生成物和交付资源，明确需要改写、删除或重新生成的内容，不能只检查定义所在文件。

目标方案应直接落实在负责该行为的位置，并同步全部消费者。不得为维持被替代方案保留兼容别名、旧入口转发、包装层、新旧格式双读双写、按旧版本选择行为的分支或失败后退回旧实现的隐式回退。目标系统需要的正常业务分支、边界适配和故障处理按其实际职责保留。

确认引用已迁移后，精确移除失效的文件、符号、依赖、配置、资源和说明，不保留备份副本、注释掉的旧代码、临时过渡层或“暂时兼容”的入口。认定历史残留须有已被替代、引用已迁走或与目标方案冲突等具体依据；当前没有匹配文件或暂时没有调用，本身不构成删除理由。仍有效的通用规则和明确保留的能力应继续保留。删除前核对用途和引用，采用精确、可恢复的操作，不清理宽泛目录，不覆盖任务外改动。

需要保留已有数据时，先设计单向迁移，将数据转换到目标格式，运行时只处理目标格式。不得以永久双读、双写代替迁移，也不得以干净切换为由删除用户数据。项目确实需要的迁移历史和变更记录按其职责保留，不参与运行时的新旧行为选择。

### 表达与内容组织

项目文档和代码注释面向最终系统的使用者及维护者，直接陈述有效职责、行为和约束。不记录“本次新增”“现在改为”“修改后”“先暂时”“后续再”等变更叙述、过渡安排或对话回应，也不将执行进度、临时结论和修改历史写入当前规则或实现说明。删除过程性措辞时须一并消除中间方案的含义，不能只替换词语。

同一事项在主责位置整合，必要时重写相邻段落或整个相关部分，不在文件末尾追加补充条款保留相互矛盾的旧内容。修改时通读上下文，统一术语、抽象层级和表达方式，不孤立追加风格不同的片段。

文件内容按阅读依赖和实际执行关系组织：基础信息及公共设置先于具体职责，局部覆盖和例外靠近对应内容。执行顺序、匹配优先级和覆盖关系优先于外观排序；只有顺序无关的同类条目采用稳定排序。

面向开发与运维的技术输出使用英文，包括日志、调试打印、程序异常、命令行提示、交互确认和帮助输出。注释和文档使用中文，保留必要的技术名称和标识符；注释中会被工具提取为技术输出的文本使用英文，例如命令帮助文本。

产品界面、客户可见提示、通知、邮件及其他面向最终用户的内容遵循产品语言和本地化规则。API 的稳定标识符、错误码和协议字段遵循接口契约，面向用户展示的消息遵循产品语言规则。用户输入、原始文献和业务数据保留原文，不因技术输出要求而翻译或改写。

### 注释与文件格式

配置与工程脚本的注释只保留职责标题及正确使用所必需的约束。分组标题采用简短名词短语，不附带操作步骤或方案解释；说明只补充配置无法直接表达的填写要求、单位、前提、外部依赖和副作用。不复述命令、执行顺序、键值或工具默认行为，不为实现选择辩解，不强调任务要求已经满足。删去后不影响正确使用或维护的说明应删除，描述当前配置本身不构成保留理由。

注释句末不加句号，分组注释放在对应内容上方并紧邻内容，同一职责集中成组，组间留一个空行。行内说明只用于项目已有工具约定要求的情况。不得添加装饰性分隔线、编号横幅、无意义的文件介绍、空分组或大段注释掉的旧内容；不得为自明内容强加注释，也不得在不支持注释的语法中虚构说明字段。

同类条目采用一致的命名、表达和排列方式。简单内容紧凑书写，较长内容按语义换行，不用多余空格手工对齐列。文件使用 UTF-8、LF 和末尾换行，不保留无意义的行尾空白。缩进、引号、逗号和换行遵循项目格式配置及语法要求，不另创风格，不因格式整理改变内容含义。

不得为节省 token 压缩代码、合并逻辑块或省略必要空行。格式化工具只能恢复缩进、空格等机械格式，不能替代职责划分和逻辑分组。仅对确认可由项目格式化工具确定性恢复的部分，允许使用紧凑的中间输出，并须在交付前完成格式化；逻辑分组及其空行应在编写时保留。格式化和检查通过不代表代码已经组织清楚。

### 验证计划与执行成本

验证以实际差异和完成条件为依据。先确定需要证明的行为、已有有效证据和剩余缺口，再据此选择验证方法及必要的检查范围。成体系的开发或重构先完成相关源码、契约及消费者的整体切换；实施期间以源码审查、必要的格式、静态、生成和限定编译检查为主，相关实现稳定后集中进行行为验收。不得每完成一个局部修改就重复执行全量测试、构建交付物或初始化完整环境。

启动耗时测试前，通读夹具及全部后置断言，按权威契约核对字段、状态、权限、原事项绑定、实际生效区间、邮件预算、截止时间和进程生命周期，并完成必要的编译检查。不得依据旧实现、名称或猜测编写断言，再通过长测试发现夹具错误。夹具失败与产品失败分别诊断，修正后只重跑受影响的必要场景。

相关场景复用真实环境和身份初始化，避免为每个断言或场景重复冷启动；互相影响的业务状态按场景隔离，不用共享状态掩盖依赖或减少必要覆盖。并行执行只用于独立资源。时钟、全局配置、故障注入及进程生命周期等共享资源由明确的执行者管理，完成清理并核验释放后才能交接。不得通过放宽真实预算、绕过权限、伪造业务事实或另建测试运行器提速。

已通过且未受新差异影响的检查复用其有效结论。只有新修改、真实失败或明确未覆盖的风险需要时，才补充、扩大或重复验证；限定检查通过后继续实施或交付，不循环重跑相同检查。整体验收在最终实现及消费者稳定后集中执行，失败修正后的重跑范围按实际影响确定。

统计、哈希、覆盖映射和报告只用于具体核验或交付判断，不周期刷新文件数量、重复核算不变产物或维护没有实际用途的证据材料。进度说明陈述功能结果、失败原因、实际缺口和下一步，不反复罗列测试数量、耗时及产物标识。耗时检查运行期间继续处理不依赖其结果的工作，不以反复轮询代替实施。

一次性测试和验证只确认当前任务结果，不固化为长期测试、脚本、夹具或构建入口。优先使用现有工具、临时命令或 `.cache/` 中的必要临时文件。只有验证稳定行为且具有持续回归价值的测试纳入测试套件，不为记录执行过程或证明某次修改增加永久测试。

### 产物与资源管理

检查和运行结果默认输出到终端，仅在继续执行、评审、交付或故障排查确实需要时落盘，不为每次检查创建目录或保存报告。必要的临时文档、脚本、中间结果、日志、截图、浏览器运行记录和调研材料统一归仓库根目录的 `.cache/`，不得散落在 `.local/`、`build/`、源码或文档目录。

`.cache/` 按任务或运行建立独立子目录，名称采用 `YYYYMMDDHHmm-任务或运行标识`，例如 `202610072124-ui-review`。时间戳使用创建时的本地时间，精确到分钟；后缀简短、明确且能区分任务或运行，不覆盖或混用已有目录。`.cache/` 加入 `.gitignore`，不参与源码提交或产品交付打包。

临时产物只保留仍需使用的最小材料，同一结论不重复保存终端输出、汇总报告、复制产物和中间快照。验证或排查结束后，清理无复用价值的日志、失败重跑产物、临时脚本、虚拟环境和复制文件。继续执行所需的步骤清单、恢复材料及有效证据按实际用途保留，交付时说明必要保留材料的路径和用途。

保存及输出材料前检查敏感信息，不因目录被 Git 忽略而保存或传播不必要的凭据和业务数据。清理前核对引用和运行状态，先回收实际资源，再删除对应文件；操作只针对已确认归属及用途的具体文件或任务目录，不覆盖其他任务的产物。

`.local/` 只承载本机运行所需的配置、凭据、密钥、进程状态和初始化材料，不作为临时产物目录。`build/` 只存放实际构建中间产物和正式交付产物。忽略规则只控制版本管理，不改变目录职责，也不授予任意写入或删除的权限。

### 完成核验与交付

修改结束后，重新通读完整文件和关联链路，不只检查新增行。核对目标是否落实在正确职责中、内容是否连贯、消费者是否全部同步，以及是否仍有重复说明、临时分支或历史残留。再次搜索被替代的标识和路径，逐项解释剩余命中的有效用途，不能仅因单个文件不再引用就认定清理完成。

按实际差异执行当前任务允许且适用的格式、静态、生成、构建或行为验证，如实说明执行范围和未验证部分。缺少环境时报告限制，不以跳过的检查或替代环境结果冒充真实系统证据。检查通过只证明其覆盖的事项，不代替结构审查、逻辑分块判断或完整切换核验。

尚有受影响消费者未迁移、旧行为仍可到达或关键决定未解决时，不得以局部可用认定任务完成。交付说明应明确最终变化、验证依据和实际未完成项；工作过程不回填到项目正文作为长期规则。

文件修改不自动包含 Git 提交、推送、发布或外部系统变更，这些操作须依据用户明确授权执行。

## 文档规范

文档按用途分为项目文档和任务材料。项目文档随项目长期维护，说明产品、设计、行为和使用约束；任务材料服务于当前任务的分析、执行、验证和恢复。Markdown 文件按实际用途适用相应规则。

### 项目文档

`docs/` 是项目的权威事实来源，收录已确认的产品定义、设计结论和行为约束。实现、配置、接口契约及其他说明应与对应定义一致。发现冲突时，明确差异，依据用户已确认的目标在授权范围内同步纠正，不以现有实现或其他说明自行推翻文档。用户明确提出的变更优先于既有文档。

`docs/` 不收录中间讨论、候选方案、临时结论、未决事项或待办占位。尚未确定的内容可在任务材料中记录，涉及用户决定的事项在对话中澄清，形成明确结论并获得相应文档修改授权后再写入。不得通过删除“待定”等标记将未经确认的内容包装成事实；已确认的目标设计与已验证的实现状态应明确区分，不将目标行为表述为已经实现。

项目文档应表述严谨、准确，逻辑清晰，术语、范围、条件和结论前后一致。关键概念明确界定，同一事实在主责位置统一维护，关联页面及流程通过引用保持一致。修改时通读相关内容，消除矛盾、歧义和重复定义，正文只表达有效事实与约束。

修改仓库根目录的 README 文件或新增项目 Markdown 说明文件，须获得用户明确授权。开发、修复、重构、审查、测试或提交任务本身不构成授权，不得以同步实现、补充用法或记录交付结果为由自行修改或新增。

获得授权后，只在用户指定或任务明确涵盖的范围内修改项目文档。未获授权时，直接向用户提供必要操作说明、验证结果和交付信息，不写入项目文档。

### 任务材料

任务材料统一存放于仓库根目录 `.cache/` 的任务子目录；当前任务授权包含必要材料的创建和更新，无须另行申请文档修改授权。目录组织、保留和清理遵循“产物与资源管理”。

任务材料可记录计划、候选方案、临时结论、未决事项及执行进度，并明确区分已确认事实、假设和待确认内容。任务材料不作为项目权威事实，转入项目文档时须满足项目文档的内容和授权要求。
