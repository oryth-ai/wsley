# Coherent Change

围绕完整目标组织修改，使职责、行为、调用方和相关说明一致。用于功能开发、问题修复、配置调整、脚本编写和重构，覆盖局部修改、跨文件变更及中断后的继续工作。

本技能不扩大用户授权。用户明确要求及适用项目规范中的具体约定优先；以下目录、语言和文档等规则作为未被项目具体约定覆盖时的默认规范。

## 任务管理

### 目标与范围

开始修改前，读取当前工作目录及拟修改路径适用的 `AGENTS.md` 和相关项目规范，通读受影响文件，明确目标行为、交付物、修改范围、对外名称、输入输出、配置含义及完成条件。在 Git 仓库中检查分支、工作区与暂存区差异，区分本次任务的修改、用户已有修改和其他工作。仅整理格式时保留原有行为，重构不改变任务外行为。

用户已经确认的决定持续有效，不得因现有实现采用了另一种方式而自行推翻。调整实现、精简表达或重新组织规范时，保留仍然有效的要求、约束和例外；摘要没有提及某项要求不构成取消依据。只有用户明确修正或有具体替代依据时，才调整对应内容。

关键行为或数据含义尚未确定时，先指出需要明确的事项，暂停依赖这些决定的工作，继续处理不受影响的部分。不得同时实现多个猜测方案，也不得用回退逻辑掩盖不确定性，不反复询问已明确的决定。

同一上下文内已完整读取且未变化的规范可以复用。简单修改直接执行，无须额外创建计划、报告或状态文件。

### 执行中的引导

执行中收到修改意见、补充要求或状态询问时，将其并入当前任务，只有用户明确替换原目标时才切换任务。需要先处理临时插入的事项时，保留原任务的未完成部分和下一步，处理完成后继续原任务。

在对话或已有任务状态中保留当前未完成事项、插入事项的完成结果与必要验证依据，以及是否已向用户汇报。已完成动作与持续约束分开维护：例如调整命名方式后，该调整可以结束，但用户确认的命名要求仍约束后续修改。

已有有效完成依据且未受后续变化影响的事项保持完成状态。只有用户要求重新处理、相关改动使已有证据失效，或出现具体冲突、失败时，才重新打开受影响的部分；不因收到新消息、上下文压缩或摘要再次提到该事项而重新核验。已经向用户汇报的完成结果不在每次恢复时逐项重述，交付时按需要汇总最终成果。

### 上下文恢复

上下文压缩后、接手交接摘要时，或发现关键任务依据缺失时，在继续未完成工作前，完整重读本技能和适用的 `AGENTS.md`。不能用此前读过或摘要中的摘录代替本次恢复；恢复完成后，在同一上下文内复用未变化的内容。

依据可见的用户原始要求、后续明确修正及已有任务状态，恢复目标、交付物、范围、已确认决定、有效授权和完成条件。区分未完成事项、已完成事项和持续约束，按未完成事项确定下一步，不将最近一条已完成的请求重新当作当前任务。压缩不重启任务，也不新增或撤销已有决定与授权。

根据恢复后的未完成目标和下一步，重新识别仍适用的专项技能，依据当前可用技能信息定位并完整重读其 `SKILL.md`，再继续对应工作。按当前步骤需要读取技能引用的资料、项目规范与接口契约；技能名称、描述、历史读取记录或摘要中的摘录不能替代完整指令。

专项技能按下一步的实际需要恢复，不照搬历史使用列表，不加载只服务于无关任务或已完成插入事项的技能，也不因此重新检查或汇报已完成事项。恢复技能只用于继续当前授权范围内的工作，不重新启动其曾经处理的任务。

摘要用于定位已有工作和待办，可以承接任务状态及已有验证结论，但不构成新的用户指令或授权，也不能将推测、候选方案或未决事项当作已确认事实。不因原始执行记录已被压缩就要求重新证明所有完成项；与直接用户要求、项目规范或实际状态存在具体冲突，或有证据失效迹象时，才核对对应来源，不按摘要覆盖原要求。原始对话不可见时，可依据摘要继续，只澄清真正影响下一步正确性、范围或授权的关键缺口，其余工作继续推进。

核对当前工作目录、分支、工作区与暂存区差异，重读下一步依赖的文件。对文件修改、测试结论、进程和后台任务，只在下一步依赖或有具体变化依据时确认当前状态。保留期间发生的用户修改，不用旧摘要覆盖实际工作，不因恢复而重建环境、重启任务或重跑全部检查，复用仍有效的结果和运行环境。

将下一步与恢复后的目标、规范及授权范围对齐；发现偏离时，纠正本任务范围内的计划或实现，不扩大任务，不重置或清理其他工作。必要的进度说明只交代当前目标、实际缺口和下一步，不重复已完成步骤、逐项播报已汇报结果或为每次恢复新增报告。

## 设计与实现

### 职责与结构

方案设计应以完整目标和必要约束为依据：判断从头实现该目标时，应如何组织目录、划分职责、定义接口和编写内容，再据此调整现有实现。现有文件用于核对事实和依赖关系，不能仅因某种设计已经存在就认定它合理。方案应直接、清晰、可维护，不以改动行数最少为标准，也不为假设中的未来需求增加抽象。

局部修改也应符合整体结构。如果新增功能需要绕过既有职责、经过无实际作用的转发层、复制逻辑或不断增加特殊分支，应先调整相关职责并重构必要部分。不得靠叠加补丁掩盖结构问题。重构范围限定于当前目标及其必要影响，不借机重写无关模块。

目录、文件、模块和函数都应有明确职责。相关内容集中维护，新增功能归入负责该行为的模块；职责不同或需要独立维护的内容应合理拆分。不得增加没有实际作用的嵌套目录或转发层，不得过度拆分，也不得以简洁为由将不同职责混放在同一个文件中。

创建文件前，说明其实际用途。文件应承载明确内容，或满足语言、构建、运行的实际要求；不得为了套用模板、凑齐目录形式或预想中的将来用途而创建空壳文件。语言、构建或工具要求保留的文件，不得仅因内容为空而删除。

### 依赖与完整切换

完整切换要求受影响范围内的实现、调用方和相关说明全部采用目标方案，并移除被替代的路径及其残留。新增代码或新入口能够运行，不代表切换完成。

修改前，搜索受影响的名称、路径、字段、配置项和入口，梳理调用与引用关系。凡调用相关功能、读取配置、依赖输出或描述行为的代码和材料，都属于需要同步的范围。检查应覆盖相关源码、配置、脚本、文档、生成物和交付资源，明确哪些内容需要改写、删除或重新生成，不能只检查定义所在的文件。

在负责该行为的位置直接实现目标方案，并同步所有调用方及关联内容。不得为维持被替代的方案而保留兼容别名、旧入口转发、包装层、新旧格式双读双写、按旧版本选择行为的分支，或失败后退回旧实现的隐式回退。目标系统需要的正常业务分支、边界适配和故障处理，按其实际职责保留。

确认引用已迁移后，逐项移除失效的文件、符号、依赖、配置、资源和说明，不保留备份副本、注释掉的旧代码、临时过渡层或“暂时兼容”的入口。认定某项内容属于历史残留，须有已被替代、引用已迁移或与目标方案冲突等具体依据。不得仅因当前没有匹配文件或暂时没有调用方，就将其视为历史残留。仍然有效的通用规则和明确保留的能力应继续保留。删除前核对用途和引用，采用范围明确、可恢复的操作，不笼统清理整个目录，不覆盖任务范围外的改动。

需要保留已有数据时，先设计单向迁移，将数据转换为目标格式，运行时只处理目标格式。不得以永久双读、双写代替迁移，也不得以完整切换为由删除用户数据。项目确实需要的迁移历史和变更记录按其职责保留，不用于在运行时选择新旧行为。

## 内容与文件规范

### 内容组织

项目文档和允许保留的代码注释面向系统的使用者及维护者，直接说明最终系统的职责、行为和约束。不使用“本次新增”“现在改为”“修改后”“暂时先用”“后续再改”等措辞记录变更、过渡安排或对话回应，也不将执行进度、临时结论和修改历史写入现行规则或实现说明。清理过程性表述时，须同时清理对应的中间方案和过渡安排，不能只替换词语。

同一事项应在负责该事项的文件或章节中统一说明，必要时重写相邻段落或整个相关部分。不得只在文件末尾追加补充条款，却保留相互矛盾的旧内容。修改时通读上下文，统一术语、抽象层级和表达方式，不孤立地追加风格不同的片段。

文件内容按理解所需的先后顺序和实际执行关系组织：基础信息及公共设置放在具体内容之前，局部覆盖和例外放在对应内容附近。排列时优先保证执行顺序、匹配优先级和覆盖关系正确；只有顺序不影响含义的同类条目才采用稳定排序。

### 语言约定

面向开发与运维的技术输出使用英文，包括日志、调试输出、异常消息、命令行提示、交互确认和帮助文本。注释和文档使用中文，保留必要的技术名称和标识符。注释中会被工具提取为技术输出的文本使用英文，例如命令帮助文本。

产品界面、客户可见提示、通知、邮件及其他面向最终用户的内容，遵循产品语言和本地化规则。API 的稳定标识符、错误码和协议字段遵循接口契约；展示给用户的消息遵循产品语言规则。用户输入、原始文献和业务数据保留原文，不因技术输出的语言要求而翻译或改写。

### 注释与文件格式

代码按职责和处理阶段分块，紧密相关的语句放在同一块，块间保留空行。声明、初始化和执行逻辑同样按职责分组，不因语法形式相同而集中堆放，也不机械地逐行留空。不同处理阶段应有清晰分隔，紧密相关的逻辑不得被无意义地拆散。函数、类型和模块的边界应便于理解和维护，不由输出长度或文件数量指标决定。

代码通过命名、职责划分和控制流程表达意图，不编写说明性注释或文档字符串。实现难以理解时，应先改善结构，不用注释解释曲折的逻辑。语言或工具必需的指令不属于说明性注释，脚本的实现逻辑同样应通过清晰的结构表达。

配置与工程脚本的注释只保留职责标题和正确使用所必需的约束。分组标题采用简短的名词短语，不附带操作步骤或方案解释；说明只补充配置本身无法表达的填写要求、单位、前提、外部依赖和副作用。不复述命令、执行顺序、键值或工具默认行为，不解释为何选择某种实现，也不强调任务要求已经满足。删除不影响正确使用或维护的说明；仅仅描述当前配置，不构成保留理由。

注释句末不加句号。分组注释放在对应内容的正上方，同一职责的内容集中成组，组间留一个空行。仅在项目已有工具约定要求时使用行内说明。不得添加装饰性分隔线、编号横幅、无实际作用的文件介绍、空分组或大段注释掉的旧内容；不得为含义明确的内容强加注释，也不得在不支持注释的语法中虚构说明字段。

同类条目采用一致的命名、表达和排列方式。简单内容紧凑书写，较长内容按语义换行，不用多余空格手工对齐列。文件使用 UTF-8 编码和 LF 换行，末尾保留换行，不保留无意义的行尾空白。缩进、引号、逗号和换行遵循项目格式配置及语法要求，不另创风格，不因格式整理改变内容含义。

不得为节省 token 而压缩代码、合并逻辑块或省略必要空行。格式化工具只能恢复缩进、空格等机械格式，不能替代职责划分和逻辑分组。只有确认项目格式化工具能够准确恢复的部分，才允许使用紧凑的中间输出，并须在交付前完成格式化。逻辑分组及其空行应在编写时保留，格式化和检查通过不代表代码已经组织清楚，也不能代替合理设计或行为核验。

## 文档与任务材料

文档按用途分为项目文档和任务材料。项目文档随项目长期维护，说明产品、设计、行为和使用约束；任务材料用于当前任务的分析、执行、验证和恢复。Markdown 文件按实际用途遵循相应规则。

### 项目文档

`docs/` 是项目的权威事实来源，收录已确认的产品定义、设计结论和行为约束。实现、配置、接口契约及其他说明应与对应定义一致。发现冲突时，先指出差异，再依据用户已确认的目标，在授权范围内同步纠正。不得仅依据现有实现或其他说明自行推翻文档；用户明确提出的变更优先于既有文档。

`docs/` 不收录中间讨论、候选方案、临时结论、未决事项或待办占位。尚未确定的内容可以记录在任务材料中；需要用户决定的事项，应在对话中澄清，形成明确结论并获得相应文档修改授权后，再写入项目文档。不得通过删除“待定”等标记，将未经确认的内容包装成事实。已确认的目标设计与已验证的实现状态应明确区分，不将目标行为表述为已经实现。

项目文档应表述严谨、准确，逻辑清晰，术语、范围、条件和结论前后一致。关键概念应有明确定义，同一事实集中维护，关联页面及流程通过引用保持一致。修改时通读相关内容，消除矛盾、歧义和重复定义，正文只陈述有效事实与约束。

修改仓库根目录的 README 文件，或新增项目 Markdown 说明文件，须获得用户明确授权。开发、修复、重构、审查、测试或提交任务本身不包含这项授权，不得以同步实现、补充用法或记录交付结果为由自行修改或新增。

获得授权后，只在用户指定或任务明确涵盖的范围内修改项目文档。未获授权时，直接在对话中提供必要的操作说明、验证结果和交付信息，不写入项目文档。

### 任务材料

当前任务的授权包含必要任务材料的创建和更新，无须另行申请文档修改授权。材料的目录组织、保留和清理遵循“产物目录与清理”的要求。

任务材料可以记录计划、候选方案、临时结论、未决事项及执行进度，并明确区分已确认事实、假设和待确认内容。任务材料不作为项目的权威事实来源；转入项目文档时，须满足项目文档的内容和授权要求。

## 验证与资源管理

### 验证计划与执行

验证以实际差异和完成条件为依据。先明确需要证明的行为、已有的有效证据和仍缺少的证据，再选择验证方法和必要的检查范围。开发或重构涉及多个关联部分时，先完成相关源码、契约、调用方及关联内容的整体切换。实施期间以源码审查和必要的格式检查、静态检查、生成检查及限定范围的编译检查为主，实现稳定后集中进行行为验收。不得每完成一处局部修改就重复执行全量测试、构建交付物或初始化完整环境。

启动耗时测试前，通读测试夹具和全部后置断言，按权威契约核对测试涉及的字段、状态、权限、对象关联、实际生效区间、预算限制、截止时间和进程生命周期，并完成必要的编译检查。不得依据旧实现、名称或猜测编写断言，再靠长时间运行测试发现夹具错误。测试夹具问题与产品问题应分别诊断，修正后只重跑受影响的必要场景。

相关场景应复用已初始化的真实环境和身份，避免为每个断言或场景重复冷启动。互相影响的业务状态按场景隔离，不用共享状态掩盖依赖或减少必要覆盖。只有使用独立资源的任务才能并行执行。时钟、全局配置、故障注入及进程生命周期等共享资源应明确由谁管理，完成清理并确认资源已释放后才能交接。不得通过放宽实际预算限制、绕过权限、伪造业务事实或另建测试运行器来提速。

已经通过且未受后续修改影响的检查，应复用其有效结论。只有出现新修改、实际失败或明确未覆盖的风险时，才补充、扩大或重复验证。必要范围内的检查通过后，继续实施或交付，不循环重跑相同检查。最终实现、调用方及关联内容稳定后，集中执行整体验收；失败修正后的重跑范围按实际影响确定。

统计、哈希、覆盖映射和报告只用于具体核验或交付判断。不得反复统计文件数量、重复核算未变化的产物，或维护没有实际用途的证据材料。进度说明应交代功能结果、失败原因、实际缺口和下一步，不反复罗列测试数量、耗时及产物标识。耗时检查运行期间，继续处理不依赖其结果的工作，不以反复轮询代替实施。

仅用于确认当前任务结果的一次性测试和验证，不保留为长期测试、脚本、夹具或构建入口。优先使用现有工具、临时命令或 `.cache/` 中的必要临时文件。只有验证稳定行为且具有持续回归价值的测试，才纳入测试套件；不为记录执行过程或证明某次修改而增加永久测试。

### 产物目录与清理

检查和运行结果默认输出到终端，只有后续执行、评审、交付或故障排查确实需要时才保存为文件，不为每次检查创建目录或保存报告。必要的临时文档、脚本、中间结果、日志、截图、浏览器运行记录和调研材料，统一存放在仓库根目录的 `.cache/` 中，不得散落在 `.local/`、`build/`、源码或文档目录。

在 `.cache/` 中按任务或运行建立独立子目录，名称采用 `YYYYMMDDHHmm-任务或运行标识`，例如 `202610072124-ui-review`。时间戳使用创建时的本地时间，精确到分钟；名称后缀应简短、明确，能够区分任务或运行，不覆盖或混用已有目录。`.cache/` 应加入 `.gitignore`，不纳入源码提交或产品交付包。

临时产物只保留仍需使用的必要材料，不为同一结论重复保存终端输出、汇总报告、产物副本和中间快照。验证或排查结束后，清理无复用价值的日志、失败和重跑产生的临时产物、临时脚本、虚拟环境及复制文件。后续执行所需的步骤清单、恢复材料及有效证据按实际用途保留，交付时说明保留材料的路径和用途。

保存或输出材料前，检查其中是否包含敏感信息，不因目录被 Git 忽略就保存或传播不必要的凭据和业务数据。清理前核对引用和运行状态，先释放实际资源，再删除对应文件。操作只针对已确认归属和用途的具体文件或任务目录，不覆盖其他任务的产物。

`.local/` 只存放本机运行所需的配置、凭据、密钥、进程状态和初始化材料，不用作临时产物目录。`build/` 只存放构建过程中产生的中间产物和正式交付产物。忽略规则只控制版本管理，不改变目录职责，也不授予任意写入或删除的权限。

## 完成核验与交付

修改结束后，重新通读修改后的完整文件，并检查相关调用和引用关系，不只检查新增行。核对目标是否由合适的模块或文件负责、内容是否连贯、所有调用方及关联内容是否已同步，以及是否仍有重复说明、临时分支或历史残留。再次搜索被替代的标识和路径，逐项确认剩余匹配结果的有效用途，不能仅因某个文件不再引用就认定清理完成。

根据实际差异，执行当前任务允许且适用的格式检查、静态检查、生成检查、构建或行为验证，如实说明执行范围和未验证的部分。缺少环境时，说明具体限制，不将未执行的检查或替代环境的结果当作真实系统的验证依据。检查通过只证明其覆盖的事项，不能代替结构审查、逻辑分组判断或完整切换核验。

受影响的调用方及关联内容尚未迁移、仍能触发被替代的旧行为，或关键决定尚未明确时，不得仅因局部可用就认定任务完成。交付说明应写明最终变化、验证依据和实际未完成项。

文件修改的授权不自动包含 Git 提交、推送、发布或外部系统变更；这些操作须获得用户明确授权。

需要交接时，优先写清当前未完成目标与下一步，保留任务要求、持续约束、适用规范、下一步仍需技能的名称、位置与用途、已确认决定、实际改动、有效验证和仍在运行的工作。已完成事项保留结果、必要验证依据及是否已汇报，不列回待办；事实、假设和未确认事项分别说明。
