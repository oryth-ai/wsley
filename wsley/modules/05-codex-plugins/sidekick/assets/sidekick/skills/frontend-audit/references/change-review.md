# 变更审查

## 比较范围

从用户请求和仓库状态确定要审查的版本。先检查分支、暂存区、工作区与未跟踪文件，区分本次变更和其他工作，不默认将全部内容归为同一任务。

| 对象 | 比较依据 |
| --- | --- |
| 仅暂存内容 | `git diff --cached`，读取暂存版本的文件内容 |
| 未暂存内容 | `git diff`，读取工作区；它只描述相对暂存区的变化 |
| 全部待提交内容 | `git diff HEAD` 加未跟踪文件；同时查看暂存差异以识别同文件的混合状态 |
| 单个提交或明确区间 | 使用实际父提交、基线与目标提交，读取对应版本 |
| 分支或 PR | 按实际目标分支和评审语义确定 merge-base 或指定基线，核对目标 head |

未跟踪文件不在普通 `git diff` 中，用 `git ls-files --others --exclude-standard` 查找并读取相关内容。初始仓库没有 HEAD、浅克隆缺少基线或 PR 元数据不可用时，说明缺失项，继续可确认范围，不假定 `origin/main` 或把工作区当作目标提交。

审查提交版本时可用 `git show <revision>:<path>` 或项目现有隔离方式读取对应内容，不切换或重置用户工作区。删除、重命名与生成文件回到其真实源码和消费者追踪，不能只看新增行。

## 增加与删除

先阅读完整差异及上下文，再沿组件导出、调用方、样式、主题、翻译资源、路由、数据和状态处理追踪影响。共享变量和组件可能破坏未修改的页面，问题归因于实际引入原因，而非是否出现在新增行。

删除信号用于定位需要核对的行为，不直接判为回归：

| 变化 | 需要确认的结果 |
| --- | --- |
| 删除名称、标签、说明、live region 或表头关联 | 原有名称、关系或通知是否仍由有效机制提供 |
| 原生链接或按钮变成通用元素 | 导航、键盘、焦点、禁用与原生行为是否保留 |
| 删除焦点样式、`tabindex` 或减少动态效果规则 | 实际键盘路径、焦点可见性及偏好支持是否改变 |
| 删除 `lang`、`dir`、逻辑 CSS 或换行规则 | 支持语言、混排、窄容器与长内容是否退化 |
| token、透明度、字体或图标变化 | 真实配对对比、文字与状态可读性是否改变 |
| 文案或状态分支缩减 | 对象、单位、成本、错误、未知结果与恢复入口是否丢失 |
| 事件、请求、缓存或资源清理变化 | 重复操作、迟到响应、身份隔离和生命周期是否仍正确 |

核对等价替换：`aria-label` 可以换成有效的 `aria-labelledby`，显式角色可以由原生元素承担，焦点描边可以由清晰的其他指示替代，字符串可以迁入翻译资源。替换有效时消除对应疑点，不能因删除某个属性或命中搜索词就报问题。

跟踪深度由实际契约和影响决定，不设固定调用方数量或跳数。完整区块可从代表消费者验证共有机制，但不同的权限、内容和状态仍需核对；未完成覆盖必须说明。

## 归因与证据

区分版本关系与证据强度：

- 新增缺陷：本次引入的能力或界面存在可确认问题
- 回归：有依据表明原有行为在目标版本退化，给出对应差异或前后证据
- 原有问题：基线已存在，按请求范围说明，不归责于本次变更
- 待确认风险：触发或影响尚未得到验证，写明所缺证据

“基线没有对应功能”不能证明实现正确，“当前有问题”也不能直接证明是回归。无法运行旧版本时，可用版本源码和契约确认静态因果，明确没有取得前后运行证据；涉及实际画面、动态行为或性能结论时取得相应测量。

按用户任务和根因合并发现，标明位置、触发条件、证据、影响及建议。变更范围内发现的数据错误、安全或性能回归仍须记录，必要时衔接专项能力，不因属于界面审查而排除实际阻断。

## 修复与交付

只读任务交付发现；已授权修复时回到负责该行为的实现，核对调用方、资源和相关状态。验证覆盖目标版本的受影响流程，必要时使用 [组件状态与压力验证](../../frontend-design/references/component-states.md) 稳定复现，避免新增预览替代真实接入。

交代实际基线、目标、包含的本地变更、已覆盖消费者与未验证条件。没有发现时说明审查范围和限制，不宣告整个前端没有问题。项目规范和结构审计由 [git-review](../../git-review/SKILL.md) 负责，不以一次体验审查替代提交前规范核验。
