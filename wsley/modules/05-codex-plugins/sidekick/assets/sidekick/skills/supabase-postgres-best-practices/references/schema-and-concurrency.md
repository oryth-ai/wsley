# 结构与并发

## 类型、键与约束

金额、数量、时间、状态和标识的类型来自业务含义，明确精度、单位、时区、空值和合法范围。选择自增、UUID 或其他主键时考虑实际生成方式、索引局部性和外部可见性，不以通用模板统一全部表。

唯一性、外键、非空和检查约束表达数据库能够保护的不变量。先查询再插入不能独立保护并发唯一性；外键列是否需要索引根据连接、删除和更新路径判断。

标识符遵循项目约定，减少不必要的大小写引用。表、列和关系的定义集中在权威输入中，不维护与生成物并行的手写结构。

分区依据访问、保留和维护需要选择，核对分区裁剪、唯一约束和跨分区行为。没有相应数据规模或生命周期收益时不为套用模式引入分区。

## 事务与锁

由完整用例拥有事务，保持持锁与事务时间有界，避免在关键锁内等待远程服务。默认隔离级别是否保护目标不变量必须通过场景验证，不能把“使用了事务”当作并发安全证明。

行锁、条件更新、唯一约束、串行化隔离和 advisory lock 服务于不同保证。定义稳定加锁顺序，处理死锁或序列化失败时沿原事项有界重试，不生成新的业务身份。

`SKIP LOCKED` 适合允许跳过竞争行的工作领取场景，不适合要求完整一致视图的普通查询。领取、租约、执行、完成和恢复各有明确持久责任。

advisory lock 的键、会话或事务范围及释放方式必须清楚；它不会自动保护未遵守同一协议的写入。普通数据库事务也不能回滚外部支付、对象写入或消息交付。

## RLS 与权限

使用最小必要的表、列、函数和 schema 权限。RLS 的启用、策略角色、读写检查、拥有者与绕过角色按实际部署核对；策略正确性优先于性能。

行过滤所依赖的身份、租户和会话变量具有可信来源，在连接池复用后不会串用户。Supabase 身份函数只在真实 Supabase 环境使用，不把其返回值或服务角色假设移植到普通 PostgreSQL。

策略中的关联列和查询路径按实际计划优化。函数的执行权限、搜索路径、安全定义者语义、触发时机和错误处理单独核验，不靠函数封装绕过原对象授权。

## 数据操作

批量写入与 upsert 根据约束和业务语义设计，明确同键同参、同键异参及并发覆盖行为。冲突处理不是通用幂等协议，不能吞掉数据不一致。

删除、恢复导入和迁移使用项目规定的入口及授权，保留有效业务与审计历史。验证恢复后的序列、约束、权限、扩展和未完成责任，不只检查导入命令返回零。
