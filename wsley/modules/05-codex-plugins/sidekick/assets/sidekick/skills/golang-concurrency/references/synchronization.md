# 同步与流水线

先画出工作、数据和资源的所有权，再选择机制。下列方式互为选择，不是必须同时使用的清单。

## Channel 与退出

采用发送与接收方向限制接口能力，关闭由负责发送生命周期的一方协调。多个发送者共享出口时，待全部发送者退出后由协调者关闭，接收者不因自身结束而直接关闭发送通道。

接收关闭的 channel 会得到零值，循环使用 `value, ok` 或 `range` 判断结束；nil channel 的发送与接收会永久阻塞。`select` 中的 nil channel 可以有意关闭分支，但不能把意外未初始化当作协调协议。

消费者提前停止时，上游发送者应能响应取消或获得结束信号。`select` 同时有多个就绪分支时不保证取消优先，必须禁止取消后新副作用的业务规则由明确状态检查与提交边界实现。

避免用空 `default` 分支形成忙等；只有明确的非阻塞查询、丢弃或拒绝协议才采用它。缓冲容量依据负载和最大可接受积压确定，不能无限扩容。

## 锁与共享状态

Mutex 保护完整不变量及全部相关访问，不只保护写入。RWMutex 的读锁不能直接升级为写锁，释放后重新获取需要重新检查条件。持锁对象避免复制，锁的拥有与释放应能从控制流程看清。

原子操作只保护对应的独立状态，多个原子字段仍可能被观察为不一致组合。`sync.Map` 适用于与其访问模型相符的场景，普通 map 配合锁常更容易表达关联不变量。

`sync.Once` 表达一次性执行，不自动提供可重试初始化。`sync.Pool` 只复用可丢弃的临时对象，放回前清理状态，不用于必需缓存或资源所有权。

避免在持有业务锁时等待网络、数据库、回调或 channel。必须跨资源协调时定义锁顺序、等待预算和错误后的释放路径，不通过增加锁数量掩盖职责混杂。

## 工作组与限流

WaitGroup 的注册在相应工作可能被等待之前完成，工作结束可靠地减少计数。按项目 Go 版本使用可用 API，不让 `Wait` 与尚未注册的启动竞争。

需要错误、取消和并发限制时使用项目已有工作组机制。明确第一个错误如何传播、尚未启动的工作是否继续、已有副作用如何确认，以及所有工作何时真正退出。

计时器的停止、重置和 channel 行为按实际 Go 版本核对；热循环避免不必要地重复创建计时器。`time.Sleep` 不承担同步协议或退出确认。

## 流水线与去重

生成、转换、扇出、合并和持久交付各自有明确拥有者。并发工作者共享入口时，出口由等待所有工作者的协调者关闭；任一阶段失败后，其他阶段都能停止并被等待。

固定 worker、信号量与工作组限制分别适用于不同排队模型。先说明积压存放在哪里、是否丢弃、何时拒绝以及停机如何处理，再选择实现。

同键并发合并不等于缓存、业务幂等或跨进程去重。共享执行需要分别处理调用者取消、底层执行期限、错误和结果隔离；去重键必须包含会改变结果的身份与范围。
