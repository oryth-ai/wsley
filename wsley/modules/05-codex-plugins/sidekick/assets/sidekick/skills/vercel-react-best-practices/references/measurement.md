# 测量与归因

## 场景与比较条件

把“页面慢”落实为可重复的任务：首次访问、路由切换、输入、滚动、提交或大列表更新。记录数据规模、设备、视口、网络、身份与缓存条件，区分首次加载、hydration 和后续交互；一次本地操作不能代表真实用户分布。

复用项目已有的浏览器、构建、打包分析和遥测入口。开发模式用于诊断，接近实际交付的构建用于确认收益；固定双方依赖、编译器、功能标志与运行条件，核对是否启用了 Strict Mode、热更新或诊断插桩。

需要真实页面操作时采用 [agent-browser](../../agent-browser/SKILL.md)，无法取得交互或 trace 时说明缺口。源码可疑模式和静态工具评分只是调查线索，不能替代实际等待与成本证据。

## React 与浏览器证据

| 要回答的问题 | 优先查看 |
| --- | --- |
| 谁触发更新，哪些子树重复渲染 | React DevTools Profiler 的更新原因、组件与 commit 记录 |
| 某个子树实际花了多少渲染时间 | 项目支持的 `<Profiler>` 及其 `actualDuration`，结合输入和更新类型 |
| 点击后为何长时间没有可见反馈 | 浏览器 Performance 时间线中的事件、JavaScript、布局、绘制及资源等待 |
| 首屏为何延迟或出现瀑布 | Network、服务端追踪、资源时序与实际首屏内容 |
| 哪些代码或资源进入了客户端 | 同一生产构建的包分析、请求体积与压缩条件 |

`<Profiler>` 的 `actualDuration` 是本次已提交更新的子树渲染耗时，`baseDuration` 是根据组件最近渲染估算的完整重渲染成本，不是历史优化前的实测基线。`commitTime` 用来关联同一次提交，不是 DOM、布局或绘制的耗时；React 渲染时间不能单独解释完整交互延迟。[React Profiler 文档](https://react.dev/reference/react/Profiler)

Profiling 会增加开销，普通生产构建默认关闭相关插桩。需要生产 profiling 时采用框架和构建器支持的方式，并将其与无插桩交付测量区分，不直接改写全部 React 入口或开启生产遥测上传。

项目 React 与浏览器版本支持时，可用 React Performance tracks 将 React 更新与网络、JavaScript、事件循环放在同一时间线上。可用轨道与构建类型有关，不能假定生产 profiling 拥有开发模式全部服务端信息。[React Performance tracks](https://react.dev/reference/dev-tools/react-performance-tracks)

## 从证据到改法

先沿关键路径区分服务端等待、网络、下载、解析执行、React 渲染及浏览器布局绘制。时间线中的相关事件用于形成假设，不把相邻发生自动当作因果；只优化确实影响当前任务的部分。

根据调用和更新原因选择并行数据加载、资源拆分、状态订阅或渲染优化。减少 commit 数量不一定更快，memo 也有比较与内存成本；核对实际编译器已经完成的优化，不用更少日志或开发模式的重复调用次数代替收益。

缓存与预加载需要相同的冷、热条件，记录必要资源是否只是移到操作之后。改变 Suspense、流式边界或虚拟化时，核对可用内容、焦点、滚动、加载和错误反馈，避免首屏指标改善但主要任务等待更久。

## 验收与证据

用相同输入和操作重复比较，记录用户可见等待、有关请求、资源大小、渲染或主线程成本及波动。实验室单次结果不代表线上分位数，不能把不同设备、缓存状态或构建的数值直接相比。

重走受影响的成功、失败、取消与恢复路径，核对身份切换、路由状态和 hydration。浏览器记录可能含敏感请求与页面数据，按项目材料规则保存；交付结论限定在实际场景，未验证的收益继续作为假设。
