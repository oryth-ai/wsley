# 项目文档组织

项目文档让使用者、开发者和维护者找到已确认的规则、设计及操作依据。先识别项目现有的文档入口、事实来源和内容归属，再按实际需要补充或调整。以下分类与路径展示一种可采用的组织方式，具体名称、位置和拆分深度由项目确定；文档写入遵循本技能的授权与内容要求。

## 事实来源

按事实的种类确定权威输入和消费者，明确文档、源码、配置、生成物与验证结果各自说明什么。

| 事实 | 维护位置与作用 |
| --- | --- |
| 已确认的产品范围、业务规则和设计约束 | 由所属项目文档定义，实现与其他说明遵循这些约束 |
| 接口、消息、配置或数据格式的机器可读声明 | 采用项目指定的 Schema、源码声明或其他权威输入，生成文档与客户端由该输入产生 |
| 工具版本、依赖和可执行参数 | 采用原生清单、配置及命令定义；说明文档解释用途、约束与使用方式 |
| 某个版本在具体环境中的实际结果 | 由测试和验收证据支持，记录其适用范围；任务结果按任务材料管理 |

同一事实只在主责位置定义，其他页面引用它。业务契约定义行为含义，机器可读声明表达可调用的形式，两者需要核对一致；接口字段齐全不能证明业务流程正确，当前实现也不能自动改写已确认的规则。Schema 优先或源码导出由项目选择，不预设统一生成方向。

`AGENTS.md` 提供协作入口及必要的项目约定，通过链接指向主责文档；项目通用工程规则复用所属技能。文档入口负责解释归属和导航，帮助读者找到原始定义。

## 职责划分

| 类别 | 回答的问题与主责内容 | 与其他内容的衔接 |
| --- | --- | --- |
| 产品 | 为谁提供什么能力，支持哪些场景，产品范围及对外承诺是什么 | 引用具体业务规则与体验，不规定源码布局 |
| 架构 | 系统由哪些运行单元组成，数据、调用、事务和信任边界如何划分 | 连接产品、契约与实现，具体包布局归工程说明 |
| 契约 | 术语、业务事实、状态、不变量、权限、输入输出及失败恢复如何定义 | 为服务、界面、客户端和验收提供共同语义 |
| 体验 | 不同角色如何完成任务，页面、导航、状态、反馈与可访问性如何组织 | 引用契约中的资格、期限和权限，说明它们如何呈现 |
| 工程 | 源码、依赖、工具链、持久化、安全、生成及测试如何实现和维护 | 公共约定集中维护，组件页面承接自身实现细节 |
| 运维 | 实际环境如何配置、初始化、部署、更新、诊断、备份和恢复 | 引用行为与工程约束，维护可执行步骤和运行前提 |

类别表示内容职责，不要求每类单独成目录。小项目可在少量页面中按章节表达；出现独立主题、不同维护边界或难以定位的内容时再拆分。公共规则与领域规则分开，同名业务概念按实际责任归属引用，避免建立第二份定义。

## 目录与导航

以 `docs/` 为例，具备相应内容的项目可以采用以下结构。示例文件按实际职责选用，不据此创建空页面或空目录。

```text
docs/
├── README.md
├── product/
│   └── overview.md
├── architecture/
│   └── system.md
├── contracts/
│   ├── common.md
│   └── export.md
├── experience/
│   ├── principles.md
│   └── user-journeys.md
├── engineering/
│   ├── repository.md
│   ├── development.md
│   ├── testing.md
│   └── components/
│       └── export-worker.md
└── operations/
    ├── configuration.md
    ├── deployment.md
    └── maintenance.md
```

入口页简述文档范围、事实归属及阅读路径，按读者任务链接到主责页面。目录树用于解释稳定的组织关系，链接用于进入具体定义；入口页不复制各页的规则或维护整份源码文件清单。

内容增长后，契约可按领域分组，体验可按角色或任务分组，工程可按真实组件分组，运维可按配置、部署和维护生命周期分组。领域、角色、源码单元与部署单元各有含义，不要求彼此一一对应，也不把源码目录机械复制为所有文档的目录。

## 页面内容

页面开头说明主题、适用范围及与其他页面的关系，随后按读者理解或实际操作顺序展开。需要的概念先定义，再陈述条件、规则和结果。只采用有实际内容的章节，不要求每页套用相同模板。

产品页说明使用者、目标、能力边界和承诺；架构页说明运行单元及相互关系，必要时配图展示数据归属、调用和信任边界。工程中的包名与操作命令由对应页面承接。

契约页先定义所属事实和术语，再说明状态、允许的动作、主体资格、输入输出、不变量及可观察结果。有持久状态或外部副作用时，明确并发、重复请求、失败、结果未知、重试和恢复的含义。字段单位、时间边界和错误语义按所属契约表达；公共协议集中定义，领域页面只维护自身规则。

体验页围绕角色和任务描述入口、对象范围、主要操作、状态变化及反馈，覆盖相关的加载、空结果、失败、未知结果和恢复。页面能执行什么、哪些数据可见，采用契约中的条件，不由按钮文案或页面布局另行定义。

工程页解释实际目录和职责、依赖方向、权威输入及生成消费者、运行与测试入口。版本和参数通过引用原生清单保持一致；组件页面维护自身装配、持久化和执行约束，公共流程由共同入口维护。

运维页按操作顺序说明目标环境、对象范围、前提、权限、输入与秘密来源、执行命令、预期结果和失败处理。初始化、日常启动、更新与恢复分别说明适用条件及对数据的影响。配置参考解释字段含义、必需性、单位及生效条件，步骤引用它，不重复维护同一参数表。命令成功、进程健康与业务恢复分别核验。

## 跨层维护

例如，项目提供文件导出时，产品页说明服务对象与能力范围，契约页定义可导出内容、访问资格、任务状态和结果有效期；体验页说明发起、查看进度及取得结果的路径，架构与工程页说明负责生成和存储的单元，运维页说明相关资源和清理机制。结果有效期由一个主责页面定义，其他页面引用该规则。

修改跨层行为时，先确定被改变的事实及其主责位置，再沿引用核对依赖它的页面、声明和实现。只调整实际受影响的内容，保留仍有效的约定；新增页面加入所属导航，合并或移动页面时迁移链接并清理被替代的入口。

维护完成后通读相关页面，核对术语、范围、前提、结果及链接是否一致。命令和路径对应实际入口，规则与实现之间的差异按任务要求处理；仍待决定的内容保留在对话或任务材料中，不用占位段落补齐文档结构。
