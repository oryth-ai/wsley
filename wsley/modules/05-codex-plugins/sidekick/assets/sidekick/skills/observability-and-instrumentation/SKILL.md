# Observability and Instrumentation

从用户可见行为和运营问题决定需要的信号，使用项目现有的日志、指标、追踪与告警设施。修改前遵循 [disciplined-dev](../disciplined-dev/SKILL.md)；不因使用本技能而引入完整监控平台、额外供应商或固定运行手册目录。

## 选择信号

明确当前功能需要回答什么，例如支付为何未确认、任务在哪个阶段积压、请求为何变慢、停止后哪些责任尚未完成。每个新增信号对应一个具体问题，复用已有有效信号，避免为满足数量增加事件和指标。

| 信号 | 适用问题 | 设计重点 |
| --- | --- | --- |
| 结构化日志 | 某个具体事项发生了什么 | 稳定事件名、阶段、结果、错误类别和允许记录的关联字段 |
| 指标 | 发生频率、用户影响与资源趋势 | 单位、分母、窗口、直方图边界与有限标签集合 |
| 追踪 | 跨调用和排队的时间去了哪里 | 上下文传播、关键 span、采样与异步因果关系 |
| 审计事件 | 谁对什么资源做了何种有效操作 | 业务归属、访问控制、完整性与项目保留政策 |

运行日志不自动成为资金、权限或审计事实的权威记录。

## 关联与隐私

沿用项目的请求、原操作、任务和追踪标识。新一次请求可以产生新的请求标识，重试仍关联原业务事项；不能为追踪方便更换业务身份。外来标识验证长度和格式，不将它当作认证或授权证据。

HTTP、队列与执行器传播实际需要的上下文。不同入口共用日志时，在任务起点记录入口角色，并与原事项一起传播；跨异步边界说明父子或因果关系，不依赖时间接近猜测来源。

记录字段采用允许列表，避免整个请求、响应、URL、异常对象或数据库记录直接写入遥测。秘密、令牌、密码、研究正文及不必要的个人数据不进入日志、指标和 span。标识本身也按项目敏感性与保留政策处理。

## 指标与预算

请求与外部依赖按需要观察请求率、失败率和延迟；队列、连接池、执行器及模型观察利用率、饱和、错误、排队年龄与工作完成情况。成功响应与业务最终完成分别计量，未知结果保留可查询状态。

延迟使用适合目标区间的直方图，并区分执行与排队时间。指标标签来自有限集合，例如路由模板、状态类别和固定依赖名称；用户、请求、原操作、完整 URL 和自由错误文本不能作为无限增长的标签。

核对采样、批量导出、缓冲、保留与存储成本，以及遥测设施故障时的有界行为。遥测不应破坏业务事务、阻塞正常停止或无限积压内存；关键审计事实按所属契约保证持久性。

## 告警与验证

告警围绕实际用户影响和可操作的风险，阈值、窗口与严重程度依据业务目标或测量结果。每个告警说明含义、首个检查步骤和处理责任，沿用项目已有运维资料。资源耗尽前兆也可以告警，不把所有资源指标固定降级为看板。

在隔离或已授权的环境触发成功、失败、重试、积压和恢复中受影响的路径，检查实际事件字段、计数、单位、标签数量与跨服务关联。验证告警条件、恢复条件和说明可用性；真实通知投递遵循用户授权，不因验收自动发送外部消息。

交付每个信号能回答的问题、实际验证和仍缺失的边界。区分代码中已添加埋点、采集端实际收到数据，以及告警已证明可用，不能互相替代。
