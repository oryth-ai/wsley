# Domain Modeling

用明确概念和具体业务场景检验领域模型，使术语、规则、所有权与实现一致。复用项目的权威产品、契约和架构说明，不预设术语表文件名、ADR 目录或领域拆分方式。

## 建模

1. **建立现有语言**：读取相关规则和调用链，区分用户明确的目标、文档约束和当前实现。找出一个名称表示多种事实、多个名称表示同一事实或跨模块重复定义的概念。
2. **定义概念边界**：说明业务含义、身份、事实拥有者、数量与单位、有效时间和生命周期。角色、资格、资产和内容权限等相关概念分别核对，不因实现中共用字段就视为等价。
3. **提出具体场景**：使用正常、拒绝、重复、并发、到期和失败恢复等与任务有关的例子，明确哪些状态和关系允许成立。一次讨论集中解决影响当前设计的歧义。
4. **表达不变量**：写明什么必须始终成立、由谁核验、在哪个事务或协议边界成立，以及条件变化后如何处理。区分原业务承诺与当前政策、业务事项与单次请求。
5. **对照实现**：沿入口、持久记录、消费者及测试核对模型。报告具体冲突，不自动按现有代码改写用户目标，也不凭概念相似就合并模块。

## 需要确认的事项

优先从已确认决定和项目事实中消除歧义。只有业务含义、权利或责任的关键选择仍然缺失时，提出具体场景和可比较的选项，同时继续不依赖该选择的工作。候选模型和假设保持明确标识，不提前写成正式业务规则。

模型可以包含多个上下文；记录同一名称在各自上下文中的精确含义和翻译边界，不为统一术语而强制重命名所有实现。区分需要共同原子成立的事实与可通过持久协议协调的事实，避免从领域名直接推导微服务拆分。

## 记录与交付

交付概念、拥有者、关键关系、不变量和能检验它们的业务场景，并指出代码与文档的具体偏差。只有确有收益时建议结构调整。

按任务授权更新项目已有的权威说明，关联页面通过引用复用事实。普通术语进入所属定义；只有实际做出难以逆转、有实质取舍且未来维护者需要了解原因的决定，才按项目约定记录架构决策。不自动创建第二份根目录术语表或独立业务规格。

实际修改遵循 [disciplined-dev](../disciplined-dev/SKILL.md) 和项目规范，保持相关契约、实现、调用方及验证一致。术语讨论本身不授权重构整个仓库。
