# 反例与状态机

## 解释反例

先用最小反例核对明确契约、输入前提、类型和相关状态，再判断故障性质。

| 现象 | 处理 |
| --- | --- |
| 有效输入违反明确保证 | 修复产品实现，保留反例和对应依据 |
| 输入违反明确前提 | 修复生成器范围，不直接定性为产品缺陷 |
| 性质比契约更强或与之矛盾 | 修正性质，保留产品已确认行为 |
| 边界的业务含义尚未决定 | 提出具体场景澄清，继续不依赖它的工作 |
| 只在错误夹具、未复位状态或不受控时钟下失败 | 修复测试隔离与依赖控制 |
| 与独立实现不一致但没有唯一契约 | 标明差异和不确定性，不能默认任一方正确 |

缩减可能改变可达状态和业务前提。确认反例仍属于原有效域，不把无效缩减结果当成可利用故障。浮点、无效编码、空字符、哈希与相等关系、迭代边界分别依据所属类型和协议判断。

## 有状态性质

建立足够简单且独立的参考状态，描述命令、前置条件、允许转移和观察结果。生成完整操作序列，覆盖重复、取消、失败、到期与恢复中实际支持的部分。

模型不能直接调用被测实现来计算预期结果。执行器记录实际动作与状态，区分已发生的副作用、未受理和结果未知，不把失败响应简单映射成“没有发生”。

并发或跨进程保证需要真实调度、事务和依赖证据。单线程状态机能够检验业务序列，但不能证明锁、持久化或分布式协调正确。

## 智能合约与审查

项目使用 Echidna、Medusa 等工具时，按实际授权执行环境、交易序列、参与者和重置策略。资产守恒、访问控制、供应量和状态边界来自合约承诺，不能让 harness 绕过权限或补造特权身份。

审查现有测试时逐项核对恒真断言、断言缺失、重实现、过度过滤、过弱性质及预算。问题的严重程度依据其隐藏的真实风险，不按模式名称机械定级。

报告最小反例、复现入口、契约依据和结论分类。修正完成后重放原失败与必要关联场景，不通过丢弃反例、降低预算或放宽性质结束排查。
