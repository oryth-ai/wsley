# 需求与团队协调

将初次输入、执行中反馈和恢复后的未完成工作放在同一份任务状态中处理。Mira 负责需求解释、分组、分派、变更传播与最终验收；专项技能提供方法，成员承接明确的工作，不各自重新组织整份用户请求。

## 需求归类与归属

先通读一条输入的全部内容，再结合已有工作判断各部分的含义。委婉表达的明确执行请求同样作为要求处理，不因使用建议或疑问句式就降为讨论。一条消息可以同时包含新工作、旧要求的修正和问题；编号、段落或技术领域只是表达形式，不直接决定任务组或 agent 数量。

| 输入含义 | 处理方式 |
| --- | --- |
| 空闲时给出一个或多个完整需求 | 提取目标、约束和完成条件，识别依赖与共享内容后分组 |
| 增加同一目标的细节或修复意见 | 更新原需求及其验收口径，保留未被修改的要求 |
| 追加独立目标 | 加入新的任务组，与全部未完成工作共同调度，不丢弃原任务 |
| 纠正、替换或撤销某项要求 | 定位被影响的需求，只使对应旧口径失效；明确替换全部任务时才整体切换 |
| 重复描述、重发消息或引用历史结果 | 关联已有需求，区分确认与真实变化，不重复建项或重新执行 |
| 调整顺序、要求暂停、继续或停止 | 对指定范围调整调度；范围为全部工作时同步处理所属团队 |
| 询问进度、解释原因或讨论候选方案 | 先回答问题，维持原工作状态；不把仅供讨论的候选和假设当成实施决定 |
| 指代、范围或要求存在实质冲突 | 仅澄清影响正确性和授权的部分，保留相关状态，继续不受影响的工作 |

结合语义、涉及对象和已有决定关联需求，不仅按最近一句或关键词猜测。明确修正替代对应旧要求，未提及的要求继续有效；同一消息中互相冲突且无法确定取舍时，不静默选择或同时实施两个版本。

为需要跨步骤跟踪的需求使用稳定的短标识。维护当前要求及其来源、所属项目、约束、完成条件、归属组和状态；有委派时同时关联当前修订、负责人、依赖、有效证据及是否已汇报。小任务可用简短对话承接，不强制填表、编号或保存文件。已完成、已取消和已替代的内容保留各自含义，不因新输入或摘要再次出现而回到待办。

## 分组与执行顺序

围绕可验收的完整结果分组。同一功能的界面、接口、配置、测试和说明通常属于一组；共享业务不变量或必须一起生效的变更由共同契约约束。独立结果可以分别成组，共享约束关联到所有受影响组，由明确的负责人维护公共实现，避免每组复制一份。

任务组表达交付目标，委派工作表达执行分工，技能表达方法。同一组可以由多个成员协作，一个成员也可以接续多个相关工作；不按需求条数、目录数或技能数机械分队。跨组修改同一文件不要求合并所有目标，但需要统一写入责任。

按用户指定的顺序、实际依赖和阻塞关系安排工作。依赖未满足的实现先等待，独立的阅读、分析和验证仍可推进。用户指定优先事项时，主协调者优先推进该事项，其他就绪工作按派工条件同步安排。

分组完成后简要说明当前目标、并行部分与必要的先后关系，直接推进已明确的工作，不把常规分组变成设计批准环节。

## 组织执行团队

依据 Mira 的派工条件，先判断全部未完成工作是否存在可并行的分工，再决定下一步。局部修改也可以与另一项实现或尚未完成的验证并行。只要有明确产出、依赖已就绪且文件与运行资源可以隔离，就使用宿主的子 agent 工具启动或复用成员，并依据工具返回确认实际分派和负责人。主协调者保留整体需求、分工和集成责任。

仅剩一项就绪工作、必须遵循串行依赖、用户要求串行，或宿主缺少委派工具、额度或权限时，按现有分组推进可执行的部分。共享写入无法隔离时，将修改交给同一负责人，其他成员仍可承接独立的只读工作。委派因工具或权限限制未能启动时，简要说明实际限制和当前安排。

团队规模按当前就绪工作、写入边界和宿主并发额度确定，不按额度上限填满成员。不为每组预建固定的设计、开发、测试和审查角色；复用仍适任的成员，只为有实际价值的独立工作增加成员。主协调者推进自己负责的工作、处理反馈和解除依赖，不重复实现已委派内容，也不只等待所有成员结束才检查结果。

每次分派给出完成该工作所需的上下文：

- 关联需求与任务组、当前修订或明确口径、预期结果与完成条件。
- 已确认决定、适用项目规范、技能路径、已有效的依据和验证。
- 工作目录、可读取范围、独占写入范围、共享接口、前置依赖、不得改变的内容及操作授权。
- 应返回的实际改动、验证结果、未完成项，以及完成或受阻后的消息接收者。

成员完整读取适用的 Mira、工程规范与选定技能，以委派范围为自己的任务；不因看到完整用户请求就接管其他组、重建团队或自行扩大任务。需要进一步分派时先向主协调者说明独立工作和边界，由其协调并发与授权，避免重复派发。

### 共享写入与资源

共享工作区中，一个文件或不可分离资源同一时刻只有一个写入负责人。共同配置、契约、依赖清单、生成入口和集成文件先确定负责人；其他成员通过消息提供所需变更。确需多人修改时先收回旧写入权，确认停止后再交接，不能仅因不同功能或不同代码段就假定无冲突。

跨层工作先确定共同契约及其负责人，再让消费者按已确认接口实现。尚未确定的契约阻塞依赖它的实现，不阻塞无关任务；需要隔离时使用宿主或项目支持的工作区方式，并明确结果如何进入主工作区，不默认创建多份仓库或目录。

端口、服务、测试数据库、缓存、全局配置和有副作用的工具遵循相同归属；文件路径不同不代表运行资源独立。必要的公共检查由主协调者安排在集成后执行，复用成员仍有效的局部验证。Git 暂存区、提交与推送由明确的单一执行者管理，成员不自行提交、重置、暂存或覆盖其他工作的内容；创建团队不增加 Git 或外部操作授权。

## 执行中更新需求

收到新输入后先与当前全部需求对照，更新受影响任务组的口径、依赖和完成条件，再按新的就绪工作重新分工。原来由主协调者独自执行的工作，也纳入此次判断。若原功能已改完但仍待独立验收，此时收到另一项可独立实施的改动，可以立即把验收派给子 agent，同时推进新改动。已验收完成且证据仍有效的工作保留完成状态。共用约束的变化同步到所有消费者，只将受影响的结果与验证标为失效。状态询问及时回答并继续工作。明确暂停或停止时，停止对应范围并等待恢复指令。

需求变化涉及正在执行的成员时，先传播变更。旧方向继续执行会产生无效写入或外部副作用时，通过宿主的消息、中断或取消机制停止受影响工作，确认成员及其相关操作已停止，再变更写入归属或重新派发。发送消息不证明已经停止；不能中断的操作先核对其实际结果，不并发启动替代写入。

将更新后的完整有效口径、已失效内容、可保留结果和下一步一并发送给受影响成员及其消费者，避免只转发一句孤立反馈。未受影响的成员继续原分工。多个反馈连续到达时合并为当前要求后再派发，不逐条重建团队；更换执行者前收回旧委派，避免新旧成员同时处理一份工作。

按以下阶段接续受影响事项：

| 当前阶段 | 更新后的行动 |
| --- | --- |
| 尚未开始或等待依赖 | 更新口径、优先级与依赖后保留或调整排队位置 |
| 正在执行 | 同步当前修订，按影响中断、调整或继续；保留无关进展 |
| 成员已返回、尚未集成 | 核对返回结果对应的要求修订；旧口径结果不能直接作为当前结果接受 |
| 已写入工作区或正在集成 | 读取实际差异，只调整已失效且属于该需求的部分，保留其他成员与用户的有效修改 |
| 已完成或已汇报 | 有真实变更时仅重新打开受影响范围，保留其他完成结论和汇报状态 |
| 已取消、已替代或明确暂停 | 不继续旧分工；需要恢复执行时以用户新的明确要求确定有效范围 |

迟到的成员消息同样核对修订、授权和状态。取消或替代后返回的“完成”不能恢复旧需求，也不能覆盖更新后的代码。已经发生的写入或外部副作用不因取消自动消失，说明实际状态，按当前授权纠正本任务的失效部分，不笼统回滚整个文件、工作区或用户数据。

## 集成、失败与接续

成员完成后，主协调者核对实际文件、依据与当前要求，将结果纳入相应任务组。成员的完成消息只说明委派工作返回；需求完成仍要求关联实现、消费者和必要验证一致。独立组不必等待所有组结束才集成，依赖组在其前置结果确认后继续。

成员受阻、失败或退出时先确定具体原因与已发生的改动。可由已有依据解决的缺口继续处理；需要用户决定时只等待受影响部分。重新分派前确认旧成员和操作停止、恢复已有进展与资源归属，不因超时或一次失败反复创建新成员。其他独立组继续推进。

上下文压缩或交接后，按 [Mira](../SKILL.md) 恢复要求与状态，再查询宿主中已有成员、消息及运行工作，核对当前委派和未集成结果后接续。摘要中出现成员名称不证明其仍在运行，也不证明其已停止；无法确认时先解决写入归属，不直接重派同一工作。保留有效验证、已完成及已汇报状态，不重新检查所有历史需求。

进度说明围绕当前分组、实质变化、阻塞和下一步；交付对照全部当前有效需求，分别说明已完成、未完成及用户明确暂停或取消的范围。不把单组完成作为整个请求完成，仍有可推进的已授权工作时继续处理。

剩余工作全部等待用户决定、外部条件或明确恢复要求时，说明具体缺口、保留的状态与恢复入口，将控制权交还用户，不空转等待或宣称全部完成。交付或交还前核对所属成员和运行资源，停止过时或已暂停范围内的执行，保留合法等待关系与未完成工作的归属。

分组与委派不改变材料归属；确需保存的材料采用 [任务材料组织](../../disciplined-dev/references/task-artifacts.md)，成员复用所属任务的材料，不另按 agent 建立顶层目录。
