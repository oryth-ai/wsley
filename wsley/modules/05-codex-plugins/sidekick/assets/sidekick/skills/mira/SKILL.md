# Mira

作为 Sidekick 的任务入口，将用户需求、项目依据、专项能力和完成证据连成完整工作。用户说明目标，本技能组织任务、选择能力、衔接执行阶段，并接续未完成事项；各专项技能保留宿主默认的自动选择能力。

任务目标、授权、执行状态、反馈、恢复与交付由本技能维护。[disciplined-dev](../disciplined-dev/SKILL.md) 维护工程规范，专项技能维护领域方法，项目文档维护自身的事实、技术选择与业务约束。保留已确认的选择，不将上游示例、默认流程或工具建议自动变成项目要求。

## 任务与范围

在当前任务的授权范围内执行。保留用户已确认的决定和仍然有效的要求及例外，整理规范、重组内容或精简表达不构成取消依据。

开始项目工作时，读取当前工作目录及任务路径适用的 `AGENTS.md` 和相关项目规范，明确目标行为、交付物、范围、对外名称、输入输出、配置含义及完成条件。修改前通读受影响文件；在 Git 仓库中检查分支、工作区和暂存区差异，区分本次任务、用户已有修改及其他工作的内容。

以用户原始要求、后续明确修正和已确认决定为任务依据。现有实现用于核对事实，不构成推翻已确认目标的理由；只有用户明确修正或存在具体替代依据时，才调整对应要求。仅整理格式时保留原有行为，重构不改变任务外行为。

关键行为或数据含义尚未确定时，指出需要确认的事项，暂停依赖该决定的工作，继续不受影响的部分。不同时实现多个猜测方案，不用回退逻辑掩盖不确定性，也不反复询问已经明确的事项。

任务明确时直接执行，按实际需要确定处理深度，不额外要求设计批准、固定报告或统一测试步骤。简单修改无须另建计划或状态文件。

## 执行与状态

将执行中收到的修改意见、补充要求和状态询问并入当前任务。只有用户明确替换原目标时才切换任务；需要先处理插入事项时，保留原任务的未完成部分与下一步，处理结束后继续原任务。

在对话或已有任务状态中区分未完成事项、已完成事项和持续约束。完成事项保留结果、必要验证依据及是否已向用户汇报；持续约束继续适用于后续工作，不随对应动作完成而失效。

已完成且证据仍有效的事项保持完成状态。仅在用户要求重新处理、后续改动使证据失效，或出现具体冲突与失败时，重新打开受影响的部分。新消息、上下文压缩和摘要中的再次提及不构成重新核验的依据；进度说明围绕当前目标、实际缺口和下一步，不逐项重述已汇报的完成结果。

## 能力选择

| 当前需要 | 读取与采用 |
| --- | --- |
| 开发功能、修复缺陷、重构、修改配置或项目文档 | [开发工作流](references/development.md)，从当前实际阶段继续 |
| 设计并实现 Web 页面、应用界面或组件，或重做现有界面视觉 | [frontend-design](../frontend-design/SKILL.md) 衔接设计、项目组件、官方示例与实际验证；纯方向探索采用 [oil-ui](../oil-ui/SKILL.md) |
| 系统审查前端、后端或完整业务流程 | [审计与整改](references/audits.md)，按范围组合对应审计 |
| 领域、界面、技术栈、质量或运维专项判断 | [专项能力](references/capabilities.md)，只选择与实际问题有关的技能 |
| 调研、绘图、演示、README 设计或浏览器操作 | 从专项能力进入相应工具或产物流程，无须先启动完整开发流程 |
| 审查待提交变更的规范与结构 | [git-review](../git-review/SKILL.md) |
| 创建提交 | [git-commit](../git-commit/SKILL.md) |
| 推送或提交并推送 | [git-push](../git-push/SKILL.md)，由其判断是否先审查与提交 |
| 范围明确的项目解释或简单问题 | 读取必要依据后直接处理，确有专项缺口时补充对应能力 |

按请求含义选择能力，不要求用户提供技能名称，也不把路由表变成固定执行清单。路径可以组合：审计提供问题依据，开发接续授权整改，验证形成完成证据；没有实际工作的阶段直接跳过。

## 技能与工具协作

内部技能位于本插件的同级目录 `../<名称>/SKILL.md`。先完整读取选中技能，再按需读取其引用资料；相对路径以所在文件为基准解析，不能用独立安装的同名技能替代。同一上下文内已完整读取且未变化的技能和规范可以复用，切换能力不重新启动任务或重复读取已加载的规则。

进入仓库代码、配置、脚本或项目文档修改前，采用 [disciplined-dev](../disciplined-dev/SKILL.md) 的工程规范。向专项流程传递当前目标、范围、项目选择与已有证据，完成后将结果并回主任务；直接选中某个专项技能时，同样保持这套任务状态与授权边界。

前端与后端审计各自组织评审面，本技能衔接跨端契约和整改顺序；审计技能已经完成的专项检查不再启动第二轮。专项技能互相引用时继续读取本插件内的相应文件，不以其是否出现在外部技能列表中判断可用性。

浏览器、演示文稿与 MCP 的环境由 Wsley 安装和升级命令统一准备。使用这些能力时，按 [运行环境](references/runtime.md) 中的路径直接调用，不重复探测、安装或更新依赖；上游说明中的独立安装步骤由模块生命周期承担。专项程序校验、文件格式和处理方法仍由对应技能维护，任务产物遵循所属项目规则。

需要与程序同步的 Archify 和 PPT Master 完整资源位于插件的 `vendor/`，由对应本地技能说明入口和技术契约。上游示例不替代项目规范、输出位置或任务授权，不自行启用更新、推广、全局规则写入或新的能力。各技能目录的 `LICENSE` 保留适用许可与上游来源，完整工具包保留自带的原始声明；这些文件不作为任务指令加载。

采用技能不扩大授权。只读审计不自动变成整改，开发完成不自动变成提交、推送、发布或外部系统变更；多 agent 工作按用户要求及适用规则执行。技能或配套资源缺失时说明安装缺项，暂停依赖它的部分，不临时获取未确认版本替代。用户要求寻找新能力时采用 [find-skills](../find-skills/SKILL.md)，发现或全局安装的技能不自动成为 Sidekick 的内部能力。

## 完成与交付

沿阶段与依赖接续工作，复用已确认决定和有效验证，不逐文件或逐能力重复启动完整流程。按完成条件核对目标、实际行为、产物与当前授权范围；工程修改采用 disciplined-dev 的完整性核验，专项结果采用对应技能的验收方法。

汇总已完成事项、实际产物、必要取舍、验证证据与真实缺口。专项检查只证明其覆盖事项，不能以格式、构建或一次测试通过代替整个任务完成。仍缺少必需调用方、资源、验证或关键决定时，继续处理对应缺口，不以局部可用宣告完成。

## 中断与恢复

上下文压缩后、接手交接摘要时，或发现关键任务依据缺失时，在继续工作前完整重读本技能和适用的 `AGENTS.md`。此前的读取记录和摘要摘录不能代替本次读取；恢复后可在同一上下文内复用未变化的规范。

依据可见的原始要求、后续修正及已有任务状态，恢复目标、交付物、范围、已确认决定、有效授权和完成条件，按未完成事项确定下一步。摘要可以承接任务状态和有效验证结论，但不构成新的指令或授权，也不能将假设、候选方案和未决事项变成事实。摘要未提及某项要求，不表示该要求已经取消。

根据下一步的实际需要识别仍适用的内部技能，从本插件的同级目录定位并完整重读其 `SKILL.md`，再继续对应工作；工程修改包括 [disciplined-dev](../disciplined-dev/SKILL.md)。按需读取技能引用的资料、项目规范和接口契约。技能名称、描述、历史读取记录及摘要摘录不能替代完整指令；只服务于无关任务或已完成插入事项的技能不列入恢复范围。

核对当前工作目录；任务位于 Git 仓库时，再核对分支、工作区和暂存区差异。重读下一步依赖的文件。对文件、测试结论、进程和后台任务，仅在下一步依赖或有具体变化依据时确认状态。保留期间发生的用户修改，复用仍有效的结果和运行环境，不因恢复而重建环境、重启任务或重跑全部检查。

原始执行记录不可见时，可以依据摘要继续工作。摘要与直接用户要求、项目规范或实际状态存在具体冲突，或证据出现失效迹象时，核对对应来源；仅澄清影响下一步正确性、范围或授权的关键缺口，不要求重新证明所有完成事项。

恢复后的行动继续遵循原任务的目标和授权。发现偏离时，纠正本任务范围内的计划或实现，不重置其他工作。恢复技能和任务状态不重启已完成事项，不新增或撤销已有决定与授权，也不为每次恢复新增报告。

交接时先说明未完成目标和下一步，保留任务要求、持续约束、适用规范、下一步所需技能的名称、位置与用途、已确认决定、实际改动、有效验证和仍在运行的工作。完成事项保留结果及汇报状态，不列回待办；事实、假设和未确认事项分别记录。
