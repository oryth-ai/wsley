# 开发工作流

适用于功能开发、缺陷修复、重构、配置调整和项目文档维护。任务状态与恢复采用 [Mira](../SKILL.md)，工程规范采用 [disciplined-dev](../../disciplined-dev/SKILL.md)；本流程负责按实际问题衔接专项能力，不重启已完成阶段。

## 要求与设计

承接已经确定的任务目标、支持范围和完成条件，读取实际入口及相关实现，选择当前仍缺少的设计判断。

业务概念、生命周期或责任归属不清时使用 [domain-modeling](../../domain-modeling/SKILL.md)，取得一致的术语、事实拥有者与不变量。模块边界和依赖妨碍实现或验证时使用 [codebase-design](../../codebase-design/SKILL.md)，确定负责该行为的模块、接口和测试接缝。

设计并实现 Web 页面、应用界面或组件时，由 [frontend-design](../../frontend-design/SKILL.md) 衔接项目依据、视觉决定、组件与源码、业务接入及实际验证。方向尚未确定时采用 [oil-ui](../../oil-ui/SKILL.md)；组件相关工作按实际体系选择专项能力，shadcn/ui 使用 [shadcn](../../shadcn/SKILL.md) 的官网与项目集成方法。承接已有决定和有效证据，具体改法明确时直接实施，不重复启动设计流程。

将设计结果用于实现顺序和验收场景。多模块变更按契约与依赖安排工作，不为每个文件独立维护一份设计或重复确认已经决定的事项。

## 缺陷定位

先取得能区分目标行为与实际行为的证据，再追踪输入、状态、权限、调用和外部副作用，缩小到具体责任边界。区分实现错误、配置或环境问题、夹具错误以及尚未明确的产品决定。

每次检查针对一个有证据的假设，修复负责该行为的位置。新结果推翻假设时更新原因判断，不叠加无依据的重试、兼容和回退。保留有回归价值的复现场景，验证真实触发条件及相关拒绝路径。

## 实施与专项检查

按当前技术栈选择 [capabilities.md](capabilities.md) 中有关的能力，将已确定的领域规则和模块契约作为输入。专项建议改变既有决定时，核对变更依据，再同步后续实现和验收，避免局部最佳实践破坏整体契约。

对同一能力的调用覆盖相关文件和调用方，不逐文件重复启动完整流程。跨前后端任务围绕请求、响应、错误、权限和状态变化衔接；页面完成与接口完成分别取得证据，再验证共同的用户流程。

按 disciplined-dev 的验证要求和当前变化选择项目检查、真实环境验证与必要行为测试，不按每个专项能力重复建立一套验收。

## 完成条件

核对目标行为、关联同步、结构规范和验证证据。发现真实的架构、体验或运行风险超出当前任务时，指出影响与建议，保留当前交付边界；已授权解决的必要关联问题继续处理。

开发完成后按用户实际要求进入审计、提交或推送。Git 技能接收当前任务范围、保留的其他修改及有效验证，不能把工作区全部内容自动当作本次交付。
