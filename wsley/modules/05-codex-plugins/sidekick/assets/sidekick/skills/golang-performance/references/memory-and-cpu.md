# 内存与 CPU

## 分配与所有权

用分配 profile、`B/op` 和 `allocs/op` 确认热点，再结合编译器的逃逸解释寻找原因。接口装箱、闭包、格式化和反射可能产生开销，是否逃逸或分配取决于实际版本和调用方式，不能仅凭语法替换。

已知大小时可预分配 slice 或为 map 提供合理容量提示，避免反复扩容；未知规模时先限制输入和内存预算，不按极端上限提前占满内存。切片重新取长、复用容量与创建独立副本有不同的别名关系。

小切片或子字符串可能继续持有较大的底层对象。需要保留少量数据且原对象应释放时，按实际所有权复制所需部分；不能因为出现切片就全部复制，也不能用零复制让本应独立的结果继续引用可变输入。

缩短指针 slice 或复用对象时，检查不再使用的引用是否仍被底层存储持有。必要清零既要满足生命周期和隐私要求，也要计入成本，不用隐藏存活对象的方式降低表面分配数。

## 池化

`sync.Pool` 只复用可丢弃的临时对象，取出的对象不能假定来自前一次放回，GC 也可能清理池中对象。连接、文件、必需缓存和有关闭责任的资源由独立生命周期管理。

明确谁取得、使用和归还对象，归还前重置状态，归还后不再读取或向调用者暴露底层可变缓冲。限制可保留容量，避免偶发大请求把大对象长期留在复用路径；评估并发、低命中率和清零成本。

比较池化前后实际分配、存活内存和吞吐。分配减少但 RSS 增加、竞争变重或生命周期错误时，不能单凭 `allocs/op` 下降判定改进。

## 布局与访问

连续数据、遍历顺序和减少指针追踪可能改善局部性。字段重排和 AoS/SoA 选择基于真实访问模式、对齐及对象数量，核对序列化、反射、原子对齐和对外格式约束，不仅追求最小 `Sizeof`。

多个 goroutine 更新相邻数据可能存在 false sharing，但吞吐随并发下降也可能来自真实锁竞争、带宽或调度。先取得测量依据；缓存行大小与处理器相关，不为所有字段固定填充 64 字节。

## 热点 CPU

优先减少算法工作、重复转换、热循环日志和不必要的反射，使用项目版本支持的类型化操作。保持错误诊断与协议含义，不为省分配把所有错误改成同一个值或删除必要日志。

内联、边界检查消除和反射成本通过实际编译器结果与基准核对。函数更短、值接收者或直接索引不保证更快；需要时查看匹配二进制中的汇编，不能从源码形状推断已经向量化。

`unsafe`、汇编、SIMD 或 cgo 只在确有收益且项目支持时考虑，说明平台、生命周期、对齐与维护成本。不能用固定提速阈值代替正确性判断，也不以性能需求扩展项目的架构或实验 API 支持范围。
