# 运行时与 I/O

## 连接与等待

复用拥有明确关闭责任的 HTTP 客户端、Transport 和数据库连接池。连接数、空闲连接和超时基于实际并发、目标主机、协议与服务预算设置，不复制固定参数，也不把增加连接数当作解决所有延迟的方法。

关闭响应体并按协议处理未消费内容。HTTP/1 连接复用可能需要读到 EOF，但对不可信或过大响应不能无限读取来换取复用；使用有界读取、取消和适当的连接处理。HTTP/2 等协议的行为按实际客户端核对。

请求、DNS、连接、TLS、响应头、读写和整条用例的截止时间分别分析，沿项目 context 传播取消。超时不证明外部副作用未发生，优化后仍保留原事项身份与恢复责任。

## 缓冲、流式与批量

大负载先明确大小上限与实际消费方式，再选择流式或缓冲。流式处理降低峰值内存时，也要处理部分输出、错误、取消与背压；不能把一次性原子结果变成未经确认的部分交付。

减少微小系统调用或网络往返时，计入批次等待、内存、尾延迟和部分失败成本。数据库批量写入保持事务、约束和错误映射，流水线仍有清楚的排序、并发和退出责任。

序列化热点先减少不必要字段与转换，再评估项目已采用的实现。替换 JSON 库、生成器或零复制路径时，核对未知字段、数字、空值、Unicode、错误和稳定协议，不只比较吞吐。

cgo 或 native 调用可能带来跨边界与线程成本，也可能绕开 Go 堆统计。合并调用或替换实现须验证实际语义与总资源成本，不用固定的纳秒开销或加速倍数下结论。

## GC 与内存配额

先测量分配速率、存活堆、GC CPU、停顿和进程内存，再决定是否调整运行参数。`GOGC` 在 CPU 与堆空间之间取舍；不能仅降低堆目标就宣称整体内存问题解决。

`GOMEMLIMIT` 是 Go 运行时管理内存的软限制，不是 RSS 或容器的硬上限。为 cgo、外部映射、其他进程及运行开销保留有依据的余量；限制低于实际工作集可能引起频繁 GC，也不能保证避免 OOM。参数以实际部署与测量确定，不统一设为容器内存的某个百分比。[Go GC 指南](https://go.dev/doc/gc-guide)

调整参数前核对 Go 版本、现有配置和实际容器感知行为。`GOMAXPROCS` 与 CPU 配额、调度和应用并发有关，不直接按宿主逻辑核数覆盖已有设置。配置变化和代码变化分别比较；生产调参及容量变更采用项目授权与运维流程。

## PGO 与验证

项目采用 PGO 时，使用能代表正式负载的 CPU profile，记录工具链、来源与构建关系。单个合成热点的 profile 可能让其他路径变差，比较目标场景及受影响的整体成本；不因性能审查默认新增 `default.pgo` 或更换发布构建方式。

对前后版本检查吞吐、尾延迟、CPU、堆和 RSS 等相关指标，覆盖正常、超时、取消与资源耗尽中受影响的行为。GC 停顿下降或某个请求更快，不单独证明服务容量和恢复能力已经改善。
